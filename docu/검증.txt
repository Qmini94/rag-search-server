  가장 큰 트레이드오프: Go + Python 2서버 구조                                                                                                                                                                                                      
                                                                                                                                                                                                                                                      문제: 검색할 때마다 Go → FastAPI /embed 내부 호출이 발생합니다. 임베딩 변환이 bottleneck인데 Go가 앞에 있어봤자 실질적 응답 속도는 Python에 종속됩니다. Go의 빠른 HTTP 처리 장점이 거의 의미 없음.                                                
                                                                                                                                                                                                                                                    
  현실: 이 서버는 Claude Code가 curl로 호출하는 로컬 도구입니다. 동시 요청 수십~수백이 아니라 한 번에 1건입니다. Go의 동시성 장점이 발휘될 상황이 없음.
                                                           
  대안: FastAPI 하나로 검색+색인 다 하면 서비스 1개 줄고, 내부 HTTP 호출 레이턴시도 없어지고, 유지보수도 쉬움. NHN JD 매칭 목적이면 Go로 별도 사이드 프로젝트를 만드는 게 나음.

  실사용에서 부딪힐 것들

  1. IVFFlat 인덱스 lists = 100 — 데이터 없으면 에러

  CREATE INDEX ... USING ivfflat ... WITH (lists = 100);
  IVFFlat은 데이터가 충분해야 생성 가능합니다 (최소 lists * 수십 행). 초기 색인 전에 이 인덱스 생성하면 실패하거나 품질이 나쁨. init.sql에 넣으면 안 되고, 색인 후에 별도로 생성하거나 HNSW로 바꿔야 합니다.

  → USING hnsw (embedding vector_cosine_ops) 추천. 데이터 양 무관하게 동작하고 검색 품질도 더 좋음.

  2. 재색인이 전체 삭제 후 재삽입

  "기존 청크 삭제 후 재색인"

  소스 파일 수백 개면 매번 전체 임베딩 재생성. multilingual-e5-small이 가볍다 해도 CPU에서 수백 파일 청킹+임베딩은 수 분~수십 분 걸림. 변경된 파일만 갱신하는 증분 색인이 필요합니다. 파일별 hash를 저장해서 변경 감지하면 됨.

  3. 청킹 전략이 구현 난이도 높음

  - Java: "클래스/메서드 단위 분할 + import 포함" → AST 파싱이 필요. 정규식으론 중첩 클래스, 어노테이션, 제네릭 등에서 깨짐
  - Vue: <script setup> 내부 함수 단위 분할도 마찬가지

  현실적 대안: 처음엔 고정 토큰/라인 수 + 오버랩 방식(예: 80줄 청크, 20줄 오버랩)으로 시작하고, 필요하면 점진적으로 언어별 파서 추가.

  4. multilingual-e5-small 쿼리 프리픽스

  E5 모델은 검색 시 "query: ", 색인 시 "passage: " 프리픽스를 붙여야 합니다. 이거 빠뜨리면 검색 품질이 크게 떨어짐. 계획서에 언급이 없음.

  5. 색인 대상 범위

  소스 전체를 색인하면 getter/setter, DTO 같은 노이즈가 검색 결과를 오염시킵니다. 실제로 Claude Code에 도움 되는 건:
  - 컨벤션/아키텍처 문서 (가장 가치 높음)
  - Service, Controller, Composable 등 핵심 로직
  - Entity/DTO/Config는 제외하거나 낮은 우선순위

  6. CLAUDE.md 연동 — 자동화가 안 됨

  계획대로면 개발자가 매번 수동으로 curl을 쳐야 합니다. Claude Code의 hooks(예: PreToolUse)에 자동 검색을 걸거나, CLAUDE.md에 "파일 수정 전 반드시 검색" 규칙을 넣어도 Claude가 실제로 매번 하는지는 보장 안 됨.
