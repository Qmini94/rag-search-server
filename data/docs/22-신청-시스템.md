# 신청 시스템

## 개요

장흥 반값 관광 신청 시스템이다. 관광객(비거주자)이 반값 지원을 신청하고, 관리자가 심사/승인/지급하는 전체 워크플로우를 처리한다.

### 전체 흐름

```
[사용자]                              [관리자]
동의 → 폼 입력 → 제출                  목록 조회
         ↓                              ↓
      RECEIVED ──→ APPROVED ──→ INSPECTION_DONE ──→ PAID
         │             │               │
         ↓             ↓               ↓
   RECEIPT_CANCEL   RECEIVED      SUPPLEMENT_REQ ──→ INSPECTION_DONE
                  (반려→재접수)         │                    또는
                                       ↓                APP_CANCEL
                                   APP_CANCEL
```

## 데이터 모델

### cms_apply_request

신청서 본체 테이블이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `idx` | BIGINT (PK, AI) | 신청 ID |
| `receipt_no` | VARCHAR(30), UNIQUE | 접수번호 (`yyyyMMdd-XXXXXX-NNN`) |
| `menu_id` | BIGINT, NOT NULL | 메뉴 ID |
| `applicant_name` | VARCHAR(50), NOT NULL | 신청인 이름 |
| `birth_date` | VARCHAR(6), NOT NULL | 생년월일 (6자리) |
| `phone` | VARCHAR(20), NOT NULL | 연락처 |
| `zipcode` | VARCHAR(10) | 우편번호 |
| `address1` | VARCHAR(200) | 기본 주소 |
| `address2` | VARCHAR(200) | 상세 주소 |
| `tourist_verified` | TINYINT(1) | 관광객 인증 여부 |
| `chak_card_no` | VARCHAR(30) | chak 카드번호 |
| `travel_start` | DATE, NOT NULL | 여행 시작일 |
| `travel_end` | DATE, NOT NULL | 여행 종료일 |
| `travel_place` | VARCHAR(100) | 여행 장소 |
| `agree_privacy` | TINYINT(1) | 개인정보 동의 |
| `agree_final` | TINYINT(1) | 최종 확인 동의 |
| `status` | VARCHAR(20), NOT NULL | 상태 (기본값: RECEIVED) |
| `reject_reason` | TEXT | 반려 사유 |
| `admin_memo` | TEXT | 관리자 메모 |
| `reg_id` | VARCHAR(50) | 등록자 ID |
| `reg_name` | VARCHAR(50) | 등록자 이름 |
| `reg_ip` | VARCHAR(50) | 등록자 IP |
| `created_date` | DATETIME, NOT NULL | 등록일 |
| `updated_date` | DATETIME, NOT NULL | 수정일 |

### cms_apply_companion

동반객 테이블이다. `cms_apply_request`와 1:N 관계.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `idx` | BIGINT (PK, AI) | 동반객 ID |
| `request_idx` | BIGINT (FK), NOT NULL | 신청 ID |
| `comp_name` | VARCHAR(50), NOT NULL | 동반객 이름 |
| `comp_birth` | VARCHAR(6), NOT NULL | 동반객 생년월일 |
| `delegation_yn` | VARCHAR(1), NOT NULL | 위임 동의 여부 (Y/N) |
| `tourist_verified` | TINYINT(1) | 관광객 인증 여부 |

### cms_apply_file

신분증/증빙자료 파일 테이블이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `idx` | BIGINT (PK, AI) | 파일 ID |
| `apply_idx` | BIGINT, NOT NULL | 신청 ID |
| `file_type` | VARCHAR(30), NOT NULL | 파일 유형 |
| `person_index` | INT | 인원 인덱스 (0=신청인, 1~=동반객) |
| `orig_name` | VARCHAR(500), NOT NULL | 원본 파일명 |
| `stored_name` | VARCHAR(500), NOT NULL | 저장 파일명 (UUID) |
| `content_type` | VARCHAR(100) | MIME 타입 |
| `file_size` | BIGINT | 파일 크기 (bytes) |
| `created_date` | DATETIME, NOT NULL | 업로드일 |

**file_type 값**:

| 값 | 설명 |
|---|---|
| `ID_FRONT` | 신분증 앞면 |
| `ID_BACK` | 신분증 뒷면 |
| `EVIDENCE_PHOTO` | 관광지 방문사진 |
| `EVIDENCE_RECEIPT` | 지출영수증 (chak 카드) |

### 상태 값과 전환 규칙

| 현재 상태 | 전환 가능 상태 | 설명 |
|---|---|---|
| `RECEIVED` | `APPROVED`, `RECEIPT_CANCEL` | 접수 → 승인 또는 접수취소 |
| `APPROVED` | `INSPECTION_DONE`, `SUPPLEMENT_REQ`, `RECEIVED` | 승인 → 검수완료, 보완요청, 재접수 |
| `SUPPLEMENT_REQ` | `INSPECTION_DONE`, `APP_CANCEL` | 보완요청 → 검수완료 또는 신청취소 |
| `INSPECTION_DONE` | `PAID`, `SUPPLEMENT_REQ` | 검수완료 → 지급 또는 보완요청 |
| `PAID` | `PAY_CANCEL` | 지급완료 → 지급취소 |

## API 엔드포인트

모든 엔드포인트의 기본 경로는 `/back-api/apply`이다.

### 사용자 API (ACCESS 권한)

| # | 메서드 | 경로 | 설명 | 요청 | 응답 |
|---|---|---|---|---|---|
| 1 | `POST` | `/` | 신청 등록 | `ApplyCreateRequest` (JSON) | `ApplyResponse` (201) |
| 2 | `GET` | `/{idx}` | 신청 상세 조회 | Path: idx | `ApplyResponse` |
| 3 | `GET` | `/my` | 내 신청 목록 | Query: page, size | `Page<ApplyListResponse>` |
| 4 | `DELETE` | `/{idx}` | 신청 취소 | Path: idx | void (본인+RECEIVED만) |
| 5 | `POST` | `/{idx}/files` | 신분증 업로드 | Multipart: fronts[], backs[] | void |
| 6 | `POST` | `/{idx}/evidence` | 증빙자료 업로드 | Multipart: photos[], receipts[] | void |
| 7 | `GET` | `/{idx}/files` | 파일 목록 조회 | Path: idx | `List<ApplyFileResponse>` |
| 8 | `POST` | `/verify-tourist` | 관광객 확인 | `TouristVerifyRequest` (JSON) | `TouristVerifyResponse` |

### 관리자 API (MANAGE 권한)

| # | 메서드 | 경로 | 설명 | 요청 | 응답 |
|---|---|---|---|---|---|
| 9 | `GET` | `/admin` | 메뉴별 신청 목록 | Query: menuId, page, size | `Page<ApplyListResponse>` |
| 10 | `PUT` | `/{idx}/status` | 상태 변경 | `ApplyStatusChangeRequest` (JSON) | void |
| 11 | `PUT` | `/{idx}/memo` | 메모 저장 | `ApplyMemoRequest` (JSON) | void |

### 요청 DTO

**ApplyCreateRequest**:

```
applicantName  String   필수, 50자 이내
birthDate      String   필수, 6자리 숫자
phone          String   필수, 20자 이내
zipcode        String   10자 이내
address1       String   200자 이내
address2       String   200자 이내
touristVerified Boolean 관광객 인증 여부
chakCardNo     String   30자 이내
travelStart    String   필수
travelEnd      String   필수
travelPlace    String   100자 이내
agreePrivacy   Boolean  필수
agreeFinal     Boolean
companions     List<ApplyCompanionRequest>
```

**ApplyCompanionRequest**:

```
compName        String   필수, 50자 이내
compBirth       String   필수, 6자리 숫자
delegationYn    String   Y 또는 N

```

**ApplyStatusChangeRequest**:

```
status        String   필수 (변경할 상태)

```

**TouristVerifyRequest**:

```

birthDate  String   필수, 6자리
```

**ApplyMemoRequest**:

```
adminMemo  String
```

### 응답 DTO

**ApplyResponse** (상세):

```
idx, receiptNo, menuId, applicantName, birthDate, phone,
zipcode, address1, address2, touristVerified, chakCardNo,
travelStart, travelEnd, travelPlace, status, rejectReason,
adminMemo, regId, regName, companions[], createdDate, updatedDate
```

**ApplyListResponse** (목록):

```

```

**ApplyFileResponse** (파일):


## 프론트엔드 구조

### 페이지

`pages/www/half/apply.vue` — script 타입 메뉴로 등록. slug catch-all을 우회하여 직접 라우팅한다. `ApplyMain` 컴포넌트를 렌더링한다.

### Step 흐름 (useApplyFlow)

3단계 스텝으로 구성된다.

```
Step 1: 개인정보 활용동의
  - agreePrivacy 체크 필수
  - 미동의 시 "APPLY.AGREE.REQUIRED" 알림

Step 2: 신청서 작성
  - 신청인 정보 (이름, 생년월일, 연락처, 주소)
  - 관광객 인증 (verifyTourist API 호출)
  - chak 카드번호
  - 여행 정보 (시작일, 종료일, 장소)
  - 동반객 추가/제거
  - 신분증 첨부 (신청인 + 동반객별 앞/뒷면)
  - 최종 확인 동의

Step 3: 신청서 작성 완료
  - completeData (ApplyResponse) 표시
```

### 제출 프로세스

```
1. JSON 페이로드로 POST /apply 호출
2. 응답의 idx로 신분증 파일 업로드 (POST /apply/{idx}/files)
   - FormData에 fronts[], backs[] 첨부
3. step = 3으로 전환하여 완료 화면 표시
```

### 동반객 관리

- `addCompanion()` — companions 배열에 추가 + 신분증 슬롯 추가
- `removeCompanion(index)` — companions 배열에서 제거 + 신분증 슬롯 제거
- idCards 인덱스: 0 = 신청인, 1~ = 동반객

### 상세 조회/증빙 업로드 (useApplyDetail)

| 함수 | 동작 |
|---|---|
| `fetchMyList(page, size)` | 내 신청 목록 (`GET /apply/my`) |
| `fetchDetail(idx)` | 상세 + 파일 목록 동시 조회 (`Promise.all`) |
| `uploadEvidence(idx, photos, receipts)` | 증빙자료 업로드 (`POST /apply/{idx}/evidence`) |
| `cancelApply(idx)` | 신청 취소 (`DELETE /apply/{idx}`) |

### 관리자 화면 (useAdminApply)

| 함수 | 동작 |
|---|---|
| `fetchList(menuId, page, size)` | 메뉴별 신청 목록 (`GET /apply/admin`) |
| `fetchDetail(idx)` | 상세 + 파일 목록 동시 조회 |
| `changeStatus(idx, status, rejectReason?)` | 상태 변경 (`PUT /apply/{idx}/status`) |
| `saveMemo(idx, adminMemo)` | 메모 저장 (`PUT /apply/{idx}/memo`) |

## 파일 업로드

### 신분증 업로드

```
POST /back-api/apply/{idx}/files
Content-Type: multipart/form-data

fronts: 신분증 앞면 (인원 수만큼)
backs:  신분증 뒷면 (인원 수만큼)
```

- 인원 인덱스(personIndex)는 배열 순서로 결정 (0=신청인, 1~=동반객)
- 본인만 업로드 가능 (`checkApplyOwner`)

### 증빙자료 업로드

```
POST /back-api/apply/{idx}/evidence
Content-Type: multipart/form-data

photos:   관광지 방문사진
receipts: 지출영수증 (chak 카드)
```

### 파일 저장 경로

```
{uploadBasePath}/apply/{applyIdx}/{UUID}.{ext}
```

- `uploadBasePath`는 `file.upload.base-path` 설정 (기본값: `uploads`)
- 파일명은 UUID로 저장, 원본 파일명은 DB에 기록

## 관광객 확인 (verifyTourist)

```
POST /back-api/apply/verify-tourist
{ "name": "홍길동", "birthDate": "900101" }
```

현재는 stub 구현이다. 항상 `tourist: true`를 반환한다. 실제 운영 시에는 행정정보 공동이용 API와 연동하여 장흥군 거주 여부를 확인해야 한다.

- 장흥군 주민: `tourist: false` (관광객 아님 → 신청 불가)
- 비거주자: `tourist: true` (관광객 인증 완료)

## 접수번호 생성 규칙

```
{yyyyMMdd}-{6자리 랜덤 영문대문자+숫자}-{3자리 랜덤 숫자}
예: 20260703-A1B2C3-456
```

`generateReceiptNo()` 메서드에서 생성한다. UUID 앞 6자를 대문자로 변환하고, 100~999 범위의 랜덤 순번을 붙인다.
