# 보안 · 에러 처리

## 1. GlobalExceptionHandler

`config/exception/GlobalExceptionHandler.java` — `@RestControllerAdvice`로 전역 예외를 처리한다.

### 예외 → HTTP 상태코드 매핑

| HTTP 상태 | 처리 예외 클래스 | 반환 code |
|-----------|----------------|-----------|
| 400 | `MissingServletRequestParameterException`, `MethodArgumentTypeMismatchException`, `IllegalArgumentException` | 400 |
| 400 | `MultipartException` (boundary 깨짐·잘못된 Content-Type) | 400 |
| 400 | `MissingServletRequestPartException` (files 파라미터 누락) | 400 |
| 400 | `MethodArgumentNotValidException` (`@Valid` DTO 검증 실패) | 400 |
| 400 | `ConstraintViolationException` (`@Validated` 단일 파라미터 검증 실패) | 400 |
| 401 | `AuthenticationServiceException` (JWT 오류) | 401 |
| 401 | `AuthenticationException` (인증 실패) | 401 |
| 403 | `AccessDeniedException` (인가 실패) | 403 |
| 404 | `NoSuchElementException` | 404 |
| 405 | `HttpRequestMethodNotSupportedException` | 405 |
| 413 | `MaxUploadSizeExceededException` | 413 |
| 500 | `EgovBizException` (일반 비즈니스 예외) | 500 |
| **403** | **`EgovBizException` — messageKey가 `"error.board.access.*"` 로 시작** | **4030** |
| 500 | `Exception` (그 외 모든 예외) | 500 |
| 503 | `DataAccessException` (DB 접근 오류) | 503 |

### `@Valid` 에러 메시지 형식

`MethodArgumentNotValidException` 핸들러는 `BindingResult`의 모든 `FieldError`를 `"필드명: 메시지"` 형태로 쉼표 구분해 반환한다.

```
"content: 내용은 필수입니다, title: 제목은 50자 이하입니다"
```

### code 4030 — 게시글 접근 차단과 프론트 safeFetch 연동

일반 403(인가 실패)과 게시글 접근 차단을 구분하기 위해 특수 코드 `4030`을 사용한다.

- 백엔드: `EgovBizException.messageKey`가 `"error.board.access."` 로 시작하면 HTTP 상태는 `403`이지만 body의 `code` 필드를 `4030`으로 반환한다.
- 프론트: `safeFetch`의 `maybeHandleAuthError` 함수는 `apiCode`가 `401` 또는 `403`일 때만 로그인 이동·뒤로가기 처리를 수행한다. `4030`은 이 조건을 통과하지 않으므로 호출측 컴포넌트가 직접 처리(예: "잘못된 접근입니다" 토스트 표시)한다.

```java
// GlobalExceptionHandler.java
if (msgKey != null && msgKey.startsWith("error.board.access.")) {
    return ResponseEntity.status(HttpStatus.FORBIDDEN)
            .body(ApiResponse.error(4030, "잘못된 접근입니다."));
}
```

```typescript
// safeFetch.ts — maybeHandleAuthError
function maybeHandleAuthError(status: number) {
  if (status !== 401 && status !== 403) return; // 4030은 여기서 걸러짐
  // ...로그인 이동/뒤로가기 처리
}
```

## 2. XSS 방어

XSS 방어는 **필터(요청)**, **AOP(서비스 진입)**, **프론트(출력)** 세 겹으로 구성된다.

### 2-1. XssProtectionFilter (요청 본문 필터링)

`config/security/XssProtectionFilter.java` — `OncePerRequestFilter`를 상속한 서블릿 필터.

동작 순서:
1. 정적 경로(`/static/`, `/public/`, `/assets/`, `/favicon.ico`) 또는 파라미터 없는 단순 GET → 필터 건너뜀
2. Content-Type이 `application/x-www-form-urlencoded`, `multipart/form-data`, `application/json`, `text/plain`인 경우에만 `XssProtectionRequestWrapper`로 요청을 감쌈
3. 요청 파라미터와 Referer 헤더를 XSS 키워드 목록으로 검사하고, 패턴 탐지 시 HTTP 400 반환

탐지 패턴 (대소문자 무시):
```
<script, </script>, javascript:, vbscript:, onload=, onerror=, onclick=,
onmouseover=, onfocus=, onblur=, onchange=, onsubmit=, <iframe, <object,
<embed, <link, <meta, expression(, alert(, confirm(, prompt(,
document.cookie, document.write
```

`XssProtectionRequestWrapper`는 `getParameter`, `getParameterValues`, `getHeader`를 오버라이드하여 값을 반환하기 전에 위험 패턴을 제거하고 `<`, `>`, `"`, `'`를 HTML 엔티티로 이스케이프한다.

필터 등록 위치 (`JwtSecurityConfig`):
```java
.addFilterBefore(xssProtectionFilter, UsernamePasswordAuthenticationFilter.class)
```

### 2-2. HtmlSanitizerAspect — @SanitizeHtml AOP

`aop/HtmlSanitizerAspect.java` — `@Aspect` + `@Component`.

포인트컷: `kr.co.itid.cms.service.cms` 하위 패키지에서 `@Transactional`이 붙은 메서드 진입 시 동작(`@Around`).

대상 필드: 파라미터 객체의 `String` 타입 필드 중 `@SanitizeHtml` 어노테이션이 붙은 필드만 세정.

`@SanitizeHtml` 권장 대상:
- 게시판 본문 (`content`)
- 페이지/컨텐츠 에디터 HTML 필드

`@SanitizeHtml` 사용 금지:
- `title`, `writerName`, `writerEmail`, `password` 등 순수 텍스트 필드

세정 로직 (`HtmlSanitizerUtil.sanitize`):
1. `<script>` 태그, `javascript:`, `vbscript:` 프로토콜 제거
2. `on\w+=` 이벤트 핸들러 속성 제거
3. CSS `expression()` 제거
4. `script`, `object`, `embed`, `link`, `meta`, `iframe`, `frame`, `frameset`, `form`, `input`, `button`, `textarea`, `select`, `option` 태그 전체 제거
5. 처리 중 예외 발생 시 안전장치로 모든 HTML 태그를 제거하고 텍스트만 반환

### 2-3. 프론트 SafeHtml.vue + DOMPurify

`components/common/SafeHtml.vue` — HTML 콘텐츠를 안전하게 출력하는 공통 컴포넌트. `v-html` 직접 사용을 금지하고 이 컴포넌트를 통해서만 HTML을 렌더링한다.

`utils/validator.ts`의 `sanitizeHtml()` 함수가 DOMPurify를 호출한다.

DOMPurify 설정:
```typescript
{
  ALLOWED_TAGS: [...DEFAULT_ALLOWED_TAGS],      // div, span, p, br, strong, em, a, img, table, ...
  ALLOWED_ATTR: [...DEFAULT_ALLOWED_ATTR],      // href, src, alt, class, id, target, rel, ...
  ALLOW_DATA_ATTR: false,
  FORBID_SCRIPT: true,
  FORBID_TAGS: ["script", "object", "embed", "form", "input", "iframe"],
  FORBID_ATTR: ["onload", "onerror", "onclick", "onmouseover", "onfocus", "onblur"],
}
```

SSR 환경(`typeof window === "undefined"`)에서는 DOMPurify를 호출할 수 없으므로 정규식으로 `<script>`, `<iframe>` 등 위험 태그만 제거하는 최소 처리를 수행한다.

컴포넌트 스타일에서도 CSS로 이중 방어:
```css
:deep(script), :deep(iframe), :deep(object), :deep(embed) { display: none !important; }
:deep([onload]), :deep([onerror]), :deep([onclick]) { pointer-events: none !important; }
```

## 3. IP 접근 제어

### 3-1. AllowIpProperties

`config/properties/AllowIpProperties.java`

```java
@ConfigurationProperties(prefix = "cms")
public class AllowIpProperties {
    private List<String> allowedIps = new ArrayList<>();
}
```

`application.yml`의 `cms.allowed-ips` 목록으로 프론트엔드 서버 IP, 로컬 IP 등 공통 허용 IP를 관리한다. 각 사이트의 allowIp 목록 조회 후 이 목록을 추가로 합산한다.

### 3-2. SiteAccessCheckerImpl — 사이트별 IP 정책

`service/cms/core/site/impl/SiteAccessCheckerImpl.java`

판정 순서:
1. 사이트가 존재하지 않거나 삭제된 경우 → **기본 허용**
2. DB의 `site.allowIp` 목록 + `AllowIpProperties.allowedIps` 통합 → 포함되면 **무조건 허용**
3. DB의 `site.denyIp` 목록에 `all`(전체 차단) 또는 해당 IP·CIDR이 있으면 → **차단**
4. 정책 없음 → **기본 허용**

IP 목록은 `,` 또는 개행으로 구분하며, `49.254.140.0/24` 같은 CIDR 표기를 지원한다. `IpUtil.isInRange()`가 IPv4 비트마스크 연산으로 CIDR 포함 여부를 판정한다.

### 3-3. business 사이트 IP 제한 동작

`JwtAuthenticationFilter`에서 IP 체크를 수행한다. 인증 엔드포인트(`/back-api/auth/**`)는 IP 체크에서 제외된다.

```java
if (!uri.startsWith("/back-api/auth/")) {
    if (!siteAccessChecker.isIpAllowed(hostname, clientIp)) {
        writeJsonError(response, HttpServletResponse.SC_FORBIDDEN, "차단된 IP입니다.");
        return;
    }
}
```

요청 헤더 `X-Site-Hostname`으로 사이트를 식별하므로 사이트별로 독립된 IP 정책이 적용된다.

## 4. CSP 헤더 (server/middleware/security-headers.ts)

Nuxt 서버 미들웨어로 동작하며, HTML 페이지 응답에만 적용된다. API(`/api/`), 정적 파일(`/_nuxt/`, `/public/`, `.js`, `.css`, 이미지 등)에는 적용하지 않는다.

### CSP directive 목록

| Directive | 허용 출처 | 이유 |
|-----------|-----------|------|
| `default-src` | `'self'` | 기본 정책 |
| `script-src` | `'self' 'unsafe-inline'` + CDN | 에디터·컴포넌트 인라인 스크립트 허용 필요 |
| | `https://cdn.jsdelivr.net`, `https://unpkg.com` | 오픈소스 라이브러리 CDN |
| | `https://t1.daumcdn.net`, `https://postcode.map.kakao.com` | 카카오 주소 검색 API (다음 우편번호) |
| `style-src` | `'self' 'unsafe-inline'` + `https://fonts.googleapis.com`, `https://cdn.jsdelivr.net` | Google Fonts, jsDelivr CSS |
| `font-src` | `'self' https://fonts.gstatic.com https://cdn.jsdelivr.net data:` | Google Fonts 실제 폰트 파일 |
| `img-src` | `'self' data: https: blob:` | 에디터 삽입 이미지, blob 미리보기 |
| `media-src` | `'self' data: blob:` | 동영상·오디오 콘텐츠 |
| `object-src` | `'none'` | Flash 등 플러그인 전면 차단 |
| `frame-src` | `'self' https://postcode.map.kakao.com https://*.kakao.com` | 카카오 주소 검색 iframe |
| `worker-src` | `'self' blob:` | Web Worker / Service Worker |
| `form-action` | `'self'` | 폼 전송 타겟 제한 |
| `connect-src` | `'self' ${baseUrl} ${apiBase}` | 백엔드 API 연결 |
| `base-uri` | `'self'` | base 태그 하이재킹 방지 |

개발 환경에서는 `script-src`, `style-src`, `connect-src` 모두 `*`로 완전 개방하여 HMR·devtools 오류를 방지한다.

## 5. 암호화

### 5-1. StringCryptoConverter (AES-GCM)

`config/jpa/StringCryptoConverter.java` — JPA `AttributeConverter<String, byte[]>`.

```java
@Converter(autoApply = false)
public class StringCryptoConverter implements AttributeConverter<String, byte[]> {
    @Override public byte[] convertToDatabaseColumn(String attribute) { return CryptoUtil.encryptToBytes(attribute); }
    @Override public String convertToEntityAttribute(byte[] dbData)   { return CryptoUtil.decryptToString(dbData); }
}
```

`autoApply = false`이므로 엔티티 필드에 `@Convert(converter = StringCryptoConverter.class)`를 명시해야 한다. DB 컬럼 타입은 `VARBINARY` 또는 `BLOB`이다.

`CryptoUtil` 동작 (AES/GCM/NoPadding):

| 단계 | 내용 |
|------|------|
| 키 로딩 | `crypto.key.path` (yml → 시스템 프로퍼티 → 환경변수 → 기본값 `/data/egovframe-cms/install/crypto_key/crypto.key`) 경로의 HEX 파일에서 16/24/32바이트 키 로드. 첫 로드 후 `CACHED_KEY`에 캐싱(DCL 패턴) |
| 암호화 | `SecureRandom`으로 12바이트 IV 생성 → AES-GCM(128-bit 태그) 암호화 → `[version(1) | iv(12) | ciphertext]` 형태로 byte[] 반환 |
| 복호화 | 첫 바이트로 버전 확인 → IV 추출 → AES-GCM 복호화. 버전 바이트가 없으면 레거시 평문으로 처리 |
| Base64 변형 | `encryptToBase64` / `decryptFromBase64`: JDBC 동적 필드처럼 BLOB이 아닌 VARCHAR에 저장할 때 사용. 디코딩 실패 시 원본 반환(평문 호환) |

### 5-2. Pbkdf2PasswordEncoder (비밀번호 해싱)

`JwtSecurityConfig`에서 `PasswordEncoder` 빈을 등록한다.

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new Pbkdf2PasswordEncoder(
            "",       // secret (없음)
            185000,   // iteration count
            256       // hash width (bits)
    );
}
```

| 파라미터 | 값 | 설명 |
|---------|-----|------|
| secret | `""` | 추가 비밀값 없음 |
| iterations | 185,000 | NIST 권장 수준의 반복 횟수 |
| hash width | 256 bits | 출력 해시 크기 |

알고리즘: PBKDF2WithHmacSHA1(Spring 기본). Salt는 `Pbkdf2PasswordEncoder` 내부에서 자동 생성·저장한다.

## 6. CSRF

### 6-1. CookieCsrfTokenRepository 설정

`JwtSecurityConfig.filterChain`에서 CSRF 보호를 활성화한다.

```java
.csrf(csrf -> csrf
    .csrfTokenRepository(
        CookieCsrfTokenRepository.withHttpOnlyFalse()  // JS에서 쿠키 읽기 허용
    )
    .ignoringRequestMatchers(
        request -> request.getRequestURI().equals("/back-api/auth/login")
    )
)
```

`withHttpOnlyFalse()`: 프론트엔드 JavaScript가 `XSRF-TOKEN` 쿠키를 읽어 요청 헤더에 포함할 수 있도록 `HttpOnly=false`로 설정한다.

### 6-2. 로그인 엔드포인트 예외 처리

`/back-api/auth/login`은 CSRF 토큰 없이 호출되어야 하므로(최초 인증 전 상태) `ignoringRequestMatchers`로 CSRF 검증에서 제외한다.

### 6-3. 프론트 XSRF 토큰 전송

`safeFetch.ts`에서 쿠키에서 `XSRF-TOKEN` 값을 읽어 모든 요청의 `X-XSRF-TOKEN` 헤더에 자동 첨부한다.

```typescript
const XSRFToken = getCookie("XSRF-TOKEN");
if (XSRFToken) runtimeHeaders["X-XSRF-TOKEN"] = XSRFToken;
```

Spring Security의 `CookieCsrfTokenRepository`는 기본적으로 `X-XSRF-TOKEN` 헤더를 인식하므로 별도 설정 없이 동작한다.

### 6-4. 세션리스(JWT) 환경에서의 CSRF 역할

애플리케이션은 `SessionCreationPolicy.STATELESS`이므로 세션 쿠키 기반 CSRF 공격에는 원래 취약하지 않다. 그러나 인증 토큰이 쿠키(`accessToken`, `refreshToken`)에 저장되므로 SameSite 정책과 함께 CSRF 토큰을 이중 방어 수단으로 유지한다.

쿠키 보안 속성은 `SecurityConstants`에서 관리한다:

```java
public static final boolean HTTP_ONLY = true;
public static final boolean SECURE = Boolean.parseBoolean(
    System.getenv().getOrDefault("COOKIE_SECURE", "true"));  // 환경변수로 제어
```

`COOKIE_SECURE` 환경변수를 `false`로 설정하면 HTTP 개발 환경에서도 동작한다.
