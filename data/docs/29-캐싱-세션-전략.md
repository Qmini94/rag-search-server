# 캐싱 · 세션 전략

## 1. 캐시 레이어 개요

Q-CMS 백엔드는 두 가지 캐시 레이어를 병용한다.

| 구분 | 구현체 | 저장 위치 | TTL | 주요 용도 |
|------|--------|-----------|-----|-----------|
| Redis 캐시 | `RedisTemplate` / `StringRedisTemplate` | 외부 Redis 서버 | 키별 상이 | 권한, 세션, 조회수 중복 방지, 방문자 집계 |
| Spring 로컬 캐시 | `ConcurrentMapCacheManager` | JVM 힙 메모리 | **없음(무한)** | 사이트 목록, 게시판 마스터, 필드 정의 |

두 레이어는 역할이 완전히 분리되어 있다. Redis는 서버 재시작 없이 무효화·공유가 필요한 데이터를, 로컬 캐시는 변경 빈도가 낮고 DB 조회 비용을 줄여야 하는 정적 메타데이터를 담당한다.

## 2. Redis 캐시 상세

### 2-1. RedisConfig — 두 가지 RedisTemplate 빈

`RedisConfig.java`는 용도별로 두 개의 빈을 등록한다.

| 빈 이름 | 타입 | 용도 |
|---------|------|------|
| `sessionRedisTemplate` | `RedisTemplate<String, SessionData>` | 세션 데이터 저장/조회 (`sess:*`) |
| `redisTemplate` (`@Primary`) | `RedisTemplate<String, MenuPermissionData>` | 메뉴 권한 데이터 저장/조회 (`perm:menu:*`) |

두 빈 모두 키는 `StringRedisSerializer`, 값은 `GenericJackson2JsonRedisSerializer`(JSON)로 직렬화한다.

### 2-2. Redis 키 네임스페이스

`RedisConstants.java`에 모든 키 패턴과 TTL이 상수로 정의되어 있다.

| 상수명 | 키 패턴 | TTL | 용도 | 무효화 시점 |
|--------|---------|-----|------|-------------|
| `PERMISSION_KEY_PREFIX` | `perm:menu:{menuId}` | 1일 (`PERMISSION_TTL`) | 메뉴별 권한 데이터 (`MenuPermissionData`) | 권한 수정·삭제 시 (`invalidateMenuPermission`) |
| `SESSION_KEY_PREFIX` | `sess:{sid}` | `jwt.session-ttl-seconds` (슬라이딩) | 세션 데이터 (`SessionData`) | 로그아웃, 명시적 삭제 |
| `USER_SESSION_PREFIX` | `user:{userId}:sessions` | `jwt.session-ttl-seconds` | 사용자별 SID Set | 전체 세션 삭제 시 |
| `VIEW_COUNT_KEY_FORMAT` | `view:{identifier}:{menuId}:{postIdx}` | 24시간 (`VIEW_COUNT_TTL`) | 조회수 중복 방지 | TTL 만료 자동 삭제 |
| `HEALTH_CHECK_KEY` | `health:check` | 500ms | Redis 헬스 체크용 | 헬스 체크 직후 자동 만료 |
| (VisitorServiceImpl) | `visitor:{ip}:{date}:{hostname}` | 1일 (`PERMISSION_TTL` 재사용) | 일별 중복 방문 방지 | TTL 만료 자동 삭제 |
| (VisitorServiceImpl) | `visitors:daily:{date}:{hostname}:{deviceType}` | — | 일별 방문자 카운터 | — |

`DEFAULT_CACHE_TTL`(1시간)은 현재 별도 키에 직접 사용되지 않으며 확장용 예비 상수다.

### 2-3. 권한 캐시 흐름

`PermissionResolverServiceImpl.getOrBuildPermissionData(menuId)`:

1. `redisTemplate.opsForValue().get("perm:menu:{menuId}")` 조회
2. 캐시 히트: `redisTemplate.expire(key, PERMISSION_TTL)` — TTL 슬라이딩 연장 후 반환
3. 캐시 미스: DB에서 권한 조회 → `MenuPermissionData` 빌드 → Redis에 1일 TTL로 저장

무효화는 `invalidateMenuPermission(menuId)` 또는 `evictPermissionsCacheForIdsUnion()`에서 대상 메뉴와 모든 하위 메뉴의 키를 일괄 DEL한다(1000개 청크 단위).

### 2-4. RedisHealthChecker

`RedisHealthChecker.java`는 Redis 서버 상태를 능동적으로 감지한다.

- **헬스 체크 방식**: `health:check` 키에 값을 SET(TTL 500ms)한 뒤 GET으로 확인
- **상태 저장**: `AtomicBoolean isRedisHealthy`로 마지막 상태를 캐싱 (성능 최적화)
- **상태 전환 로그**: Normal → Degraded, Degraded → Normal 전환 시에만 로그 출력
- **Fallback 모드 진입**: 헬스 체크 실패 또는 Runtime 예외 발생 시 `isRedisHealthy = false`로 전환

| 상태 | `isRedisHealthy` | 동작 |
|------|-----------------|------|
| Normal | `true` | Redis 캐시 정상 읽기/쓰기 |
| Degraded | `false` | 세션 조회·touch 생략, 조회수 증가 스킵, 권한 캐시 미사용 |
| 복구 | `true` 재전환 | 자동 복구, 로그 출력 |

`isCachedRedisHealthy()`는 실제 핑 없이 `AtomicBoolean`만 읽으므로 매 요청마다 호출해도 오버헤드가 없다.

## 3. Spring 로컬 캐시 상세

### 3-1. CacheConfig

`CacheConfig.java`는 `@EnableCaching`으로 Spring Cache를 활성화하고 `ConcurrentMapCacheManager`를 빈으로 등록한다.

사전 정의된 캐시 이름:

| 캐시 이름 | 관리 서비스 | 캐시 키 | 내용 |
|-----------|------------|---------|------|
| `sites` | `SiteCacheService` | `'active'` / `'all'` | 활성·전체 사이트 목록 |
| `site` | `SiteCacheService` | `siteHostName` | 호스트명별 단일 사이트 |
| `boardMasters` | `BoardMasterCacheService` | `option + pageable` | 게시판 목록 (페이징) |
| `boardMaster` | `BoardMasterCacheService` | `idx` | 게시판 단일 조회 |
| `boardFieldDefinitions` | `BoardMasterCacheService` | `boardMasterIdx` | 커스텀 필드 정의만 |
| `boardFieldDefinitionsFull` | `BoardMasterCacheService` | `boardMasterIdx` | 프리셋 + 커스텀 전체 필드 |
| `activeBoardMasters` | `BoardMasterCacheService` | — | 활성 게시판 마스터 목록 |

`setAllowNullValues(false)` 설정으로 `null` 결과는 캐시하지 않는다.

### 3-2. TTL 없음 — 핵심 주의사항

`ConcurrentMapCacheManager`는 만료 시간을 지원하지 않는다. 한 번 캐시에 적재된 데이터는 **서버 재시작 전까지 절대 자동 만료되지 않는다.**

DB를 직접 수정(SQL/관리 콘솔)하거나 JPA로 엔티티를 변경한 뒤 캐시 무효화 메서드를 호출하지 않으면 API는 계속 이전 데이터를 반환한다.

### 3-3. @Cacheable / @CacheEvict 사용 위치

**BoardMasterCacheService**

```java
// 적재
@Cacheable(value = "boardMasters", key = "#option.toString() + '_' + #pageable.toString()")
public Page<BoardMasterListResponse> searchBoardMasters(...)

@Cacheable(value = "boardMaster", key = "#idx")
public BoardMasterResponse getBoardByIdx(Long idx)

@Cacheable(value = "boardFieldDefinitions", key = "#boardMasterIdx")
public List<BoardFieldDefinitionResponse> getFieldDefinitions(Long boardMasterIdx)

@Cacheable(value = "boardFieldDefinitionsFull", key = "#boardMasterIdx")
public List<BoardFieldDefinitionResponse> getAllFieldDefinitions(Long boardMasterIdx)

// 무효화 (전체)
@CacheEvict(value = {"boardMasters", "boardMaster", "boardFieldDefinitions",
                     "boardFieldDefinitionsFull", "activeBoardMasters"}, allEntries = true)
public void evictAllBoardMasterCache() {}
```

**SiteCacheService**

```java
@Cacheable(value = "sites", key = "'active'")
public List<SiteResponse> getActiveSites()

@Cacheable(value = "sites", key = "'all'")
public List<SiteResponse> getAllSites()

@Cacheable(value = "site", key = "#siteHostName")
public SiteResponse getSiteByHostName(String siteHostName)

@CacheEvict(value = "sites", allEntries = true)
public void evictSiteCache()

@CacheEvict(value = "site", key = "#siteHostName")
public void evictSiteCache(String siteHostName)
```

### 3-4. 캐시 무효화 트리거

게시판 마스터 생성·수정·삭제 시 서비스 레이어에서 `BoardMasterCacheService.evictAllBoardMasterCache()`를 명시 호출해야 한다. 이 메서드는 빈 구현체이며, `@CacheEvict`의 `allEntries = true` 옵션이 Spring AOP 프록시를 통해 5개 캐시를 모두 비운다.

## 4. 세션 관리

### 4-1. SessionData 구조

Redis에 저장되는 세션 객체(`sess:{sid}`):

| 필드 | 타입 | 설명 |
|------|------|------|
| `userId` | `String` | 사용자 아이디 |
| `userLevel` | `int` | 사용자 레벨 (1 = 관리자) |
| `idx` | `Long` | 사용자 인덱스 (PK) |
| `userName` | `String` | 사용자 이름 |
| `hostname` | `String` | 접속 사이트 호스트명 |
| `lastActivity` | `long` | 마지막 활동 시각 (epoch ms) |

`isAdmin()`은 `userLevel == 1`을 반환한다.

### 4-2. TTL 설정값

TTL은 `application.yml`의 `jwt.*` 프로퍼티로 주입된다(`JwtProperties`).

| 항목 | 프로퍼티 키 | 적용 위치 |
|------|------------|-----------|
| Access Token 유효기간 | `jwt.access-token-validity` (초) | JWT 서명 만료 클레임 |
| Refresh Token 유효기간 | `jwt.refresh-token-validity` (초) | Refresh Token 만료 |
| Fallback Token 유효기간 | `jwt.fallback-token-validity` (초) | Redis 장애 시 Access Token 연장 |
| 세션 슬라이딩 TTL | `jwt.session-ttl-seconds` (초) | `sess:*` 키 TTL, touch 시마다 재설정 |

세션 TTL은 슬라이딩 방식이다. 요청마다 `touchSession(sid)`을 호출하면 `lastActivity`가 갱신되고 TTL이 `sessionTtlSeconds`로 재설정된다.

### 4-3. Redis 장애 시 Fallback

`SessionManagerImpl`은 모든 Redis 연산 전에 `redisHealthChecker.isCachedRedisHealthy()`를 확인한다.

| 메서드 | Redis 장애 시 동작 |
|--------|-------------------|
| `getSession(sid)` | `Optional.empty()` 반환 (세션 없음으로 처리) |
| `touchSession(sid)` | 조용히 패스 — 요청 흐름 차단 없음 |
| `getSessionTtl(sid)` | `-1` 반환 |
| `createSession(...)` | 예외 전파 (생성 자체는 Redis 필수) |
| `deleteSession(sid)` | 예외 전파 |

Redis 장애 상황에서 세션 조회 실패는 인증 실패로 이어진다. JWT `fallback-token-validity`를 길게 설정하면 Access Token만으로 일정 시간 서비스를 유지할 수 있다.

## 5. 조회수 중복 방지

`DynamicBoardServiceImpl.tryIncreaseViewCount(user, menuId, idx)`:

```
키 패턴: view:{identifier}:{menuId}:{postIdx}
TTL    : 24시간 (VIEW_COUNT_TTL)
```

- `identifier`: 로그인 사용자는 `sessionId`, 비로그인(게스트)은 클라이언트 IP
- `SETNX`(`setIfAbsent`) 방식으로 키가 없을 때만 조회수 증가
- Redis 장애 시 예외를 캐치하고 조용히 스킵 — 조회수 증가 누락이 발생할 수 있으나 서비스 흐름은 유지

## 6. 주의사항

### 로컬 캐시 TTL 없음

`ConcurrentMapCacheManager`는 만료를 지원하지 않으므로, DB를 직접 변경(DML, 관리 콘솔)한 경우 반드시 해당 캐시 무효화 메서드를 수동 호출하거나 서버를 재시작해야 한다.

- 게시판 마스터 변경 → `BoardMasterCacheService.evictAllBoardMasterCache()` 호출
- 사이트 변경 → `SiteCacheService.evictSiteCache()` 호출

캐시 무효화 없이 DB를 직접 수정하면 API는 구 데이터를 계속 반환한다.

### Redis 장애 시 권한 캐시 미작동

`PermissionResolverServiceImpl`은 별도 헬스 체크 없이 Redis 연산을 시도하고, 실패 시 런타임 예외가 발생한다. Redis가 다운되면:

- 권한 캐시 히트 불가 → 매 요청마다 DB 조회 발생
- DB 조회가 성공하면 서비스는 유지되나 성능이 저하된다
- Redis 연결 자체가 타임아웃되면 요청 처리 지연이 발생할 수 있다

`RedisHealthChecker`는 세션 관련 경로에만 사전 체크가 적용되어 있으므로, 권한 경로는 Redis 복구를 우선 확인해야 한다.

### visitor 키 TTL 재사용

`VisitorServiceImpl`은 `PERMISSION_TTL`(1일)을 방문자 중복 방지 키 TTL로 재사용한다. 의미상 혼동할 수 있으나, 값은 동일하게 24시간이다(`VIEW_COUNT_TTL`과 동일).
