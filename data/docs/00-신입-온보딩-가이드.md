# Q-CMS 신입 온보딩 가이드

> 이 문서는 Q-CMS 프로젝트에 처음 합류한 개발자/퍼블리셔를 위한 안내서입니다.
> "왜 이렇게 만들었는지"까지 함께 설명하므로, 코드를 보기 전에 먼저 읽어두세요.

---

## 1. Q-CMS가 뭔가요?

### 비유로 이해하기

Q-CMS를 **건물을 여러 채 짓는 건설회사**에 비유할 수 있습니다.

- 건설회사(Q-CMS)는 건물(웹사이트)을 여러 채 관리합니다.
- 각 건물은 외관(디자인)도 다르고, 출입 규칙(권한)도 다르고, 내부 구조(메뉴)도 다릅니다.
- 하지만 설계 도면(코드)과 건자재(컴포넌트)는 공유합니다.

이것을 **멀티사이트 CMS**라고 부릅니다. 하나의 Nuxt 프로젝트 + 하나의 Spring Boot 서버로 여러 사이트를 동시에 운영합니다.

### 실제 사이트 구성

이 프로젝트에는 세 가지 사이트가 있습니다.

| 사이트 식별자 | 역할 | 레이아웃 파일 | CSS 방식 |
|---|---|---|---|
| `www` | 일반 사용자가 보는 공개 홈페이지 | `layouts/www-main.vue`, `www-sub.vue` | 전통 CSS (`btn_base`, `write_box` 등) |
| `business` | 관리자 전용 백오피스 | `layouts/business-sub.vue` | Tailwind CSS |
| `default` | 폴백용 기본 레이아웃 | `layouts/default-main.vue`, `default-sub.vue` | - |

URL 구조를 보면 사이트가 바로 보입니다.

```
/www/notice/list        → www 사이트의 공지사항 목록
/business/homepage/board → business 사이트(관리자)의 게시판 관리
/common/login           → 공용 로그인 페이지 (사이트 구분 없음)
```

### 왜 이렇게 만들었나요?

하나의 도메인에서 사용자 사이트와 관리자 사이트를 분리하면서도, 배포는 한 번만 하기 위해서입니다. 사이트별로 서버를 따로 두면 유지보수가 어렵고, 코드 중복이 생깁니다.

각 사이트는 독립적인 **메뉴 트리**, **권한 설정**, **CSS 테마**를 가집니다. `siteStore`에 현재 어느 사이트인지 저장해두고, 모든 미들웨어와 컴포넌트가 이 값을 참고합니다.

```ts
// stores/siteStore.ts
export const useSiteStore = defineStore("site", () => {
  const siteList = ref<Site[]>([]);
  const site = ref("www");  // 현재 활성 사이트
  // ...
});
```

## 2. 사용자가 페이지를 열면 무슨 일이 벌어지나요?

### 택배 배송에 비유하기

사용자가 `/www/notice/list` 를 브라우저에 입력한다고 생각해봅시다. 이건 택배를 주문하는 것과 같습니다.

1. **택배사 선택** (어느 사이트?) → `01.site-init` 미들웨어
2. **배송 방식 선택** (레이아웃?) → `01b.layout-setting` 미들웨어
3. **신분증 확인** (로그인 여부?) → `02.authentication` 미들웨어
4. **배송 목록 조회** (어떤 메뉴?) → `03.menu-management` 미들웨어
5. **수령 자격 확인** (권한 있음?) → `04.permission-check` 미들웨어
6. **상자 개봉** (화면 렌더링) → `pages/[...slug].vue`

Nuxt는 페이지를 서버에서 먼저 렌더링(SSR)하고, 브라우저에서 다시 활성화(CSR/하이드레이션)합니다. 미들웨어 체인은 **SSR과 CSR 양쪽에서 모두 실행**됩니다. 이 때문에 각 미들웨어에서 `import.meta.server` / `process.client` 분기가 자주 등장합니다.

### 실제 코드 경로 따라가기

#### 1단계: `middleware/01.site-init.global.ts` — "어느 건물에 왔는지 확인"

```ts
// URL에서 사이트명 추출: /www/notice → "www"
const site = extractSiteFromPath(url);

// 사이트 목록을 아직 안 불러왔으면 API 호출
if (siteStore.siteList.length === 0) {
  await siteStore.fetchSiteList();  // /api/json/site 호출
}

// Pinia 스토어에 현재 사이트 저장
siteStore.setSite(site);
```

이 미들웨어가 가장 먼저 실행되는 이유: 뒤의 모든 미들웨어가 "지금 어느 사이트냐"를 알아야 하기 때문입니다.

IP 차단 기능도 여기서 처리됩니다. SSR에서 차단된 경우 `__ipBlock=1` 쿠키를 심어두고, CSR에서도 같은 쿠키를 보고 차단합니다.

#### 2단계: `middleware/01b.layout-setting.global.ts` — "몇 층으로 안내할지 결정"

```ts
// /www → 메인 레이아웃 (홈 화면)
// /www/notice → 서브 레이아웃 (내부 페이지)
const mainCandidate = `${prefix}-main`;  // → "www-main"
const subCandidate  = `${prefix}-sub`;   // → "www-sub"

// layouts/ 폴더에 해당 파일이 있는지 확인
const KNOWN_LAYOUTS = new Set(
  Object.keys(import.meta.glob("~/layouts/*.vue"))
    .map(p => p.split("/").pop().replace(/\.vue$/, ""))
);

to.meta.layout = KNOWN_LAYOUTS.has(mainCandidate) ? mainCandidate : "default-main";
```

실제 레이아웃 파일들:
- `layouts/www-main.vue` — www 사이트 홈
- `layouts/www-sub.vue` — www 사이트 내부 페이지
- `layouts/business-sub.vue` — 관리자 사이트 (main/sub 구분 없이 하나)

#### 3단계: `middleware/02.authentication.global.ts` — "출입증 확인"

```ts
await userStore.initUser();  // /back-api/auth/me 호출로 JWT 검증

const isSiteClosed = matchedSite?.isOpen === false;
const isAdmin = userStore.isAdmin;   // level === 1 이면 관리자
const isGuest = userStore.isGuest;   // idx === -1 이면 비로그인

// 사이트가 닫혀있고 관리자가 아니면 → 로그인 페이지로
if (isSiteClosed && !isAdmin) {
  return navigateTo(`/common/login?...`);
}
```

#### 4단계: `middleware/03.menu-management.global.ts` — "어떤 방을 보여줄지 결정"

```ts
// 메뉴 트리 로딩 (사이트별 1회, 캐싱)
await menuStore.fetchMenuTree(site);  // /api/json/menu?site=www

// 현재 URL과 일치하는 메뉴 찾기
menuStore.setCurrentMenuByPath(normalized);

// 폴더 메뉴면 첫 번째 자식 메뉴로 리다이렉트
const effective = getEffectiveRoutePath(matched);
if (effective !== normalized) {
  return navigateTo(effective);
}
```

#### 5단계: `middleware/04.permission-check.global.ts` — "이 방에 들어갈 권한 확인"

```ts
// 현재 메뉴에 대한 렌더 데이터 + 권한 정보 로딩
await renderStore.fetchRenderData();  // /back-api/render

// URL 쿼리의 mode에 따라 권한 검사
// ?mode=list → access 권한, ?mode=write → write 권한
const hasAccess = permission[mode] ?? permission.access;

if (!hasAccess) {
  return navigateTo("/common/login?...");
}
```

#### 6단계: `pages/[...slug].vue` — "최종 방 열기"

```vue
<!-- pages/[...slug].vue -->
<Board v-if="isBoard" />        <!-- type === "board" -->
<Content v-else-if="isContent" /> <!-- type === "content" -->
```

`renderStore.data.type` 값에 따라 게시판(`Board.vue`) 또는 콘텐츠(`Content.vue`)를 렌더링합니다.

## 3. 메뉴 시스템 쉽게 이해하기

### 파일 탐색기에 비유하기

관리자가 메뉴를 만들 때 선택하는 타입은 마치 파일 탐색기와 같습니다.

| 메뉴 타입 | 파일 탐색기 비유 | 실제 동작 |
|---|---|---|
| `folder` | 폴더 | 자식 메뉴를 담는 그릇. 직접 접근하면 첫 자식으로 리다이렉트 |
| `board` | 엑셀 파일 | 게시판 데이터 표시. `Board.vue` 렌더러 사용 |
| `content` | 메모장 파일 | HTML 콘텐츠 표시. `Content.vue` 렌더러 사용 |
| `script` | 실행 파일(.exe) | `pages/{site}/` 에 직접 만든 Vue 페이지로 연결 |
| `link` | 바로가기 | 외부 또는 내부 URL로 이동 |

타입 정의는 `types/site/menu.ts`에서 확인할 수 있습니다.

```ts
// types/site/menu.ts
export interface MenuItem {
  id: number
  parentId: number
  title: string
  type: 'folder' | 'board' | 'content' | 'script' | 'link'
  value: string      // 게시판ID, 콘텐츠ID, URL 등 타입별 실제 값
  isShow: boolean    // GNB/LNB에 표시 여부
  pathUrl: string    // "0|notice|list" 같은 계층 경로
  children?: MenuItem[]
}
```

### 메뉴 타입별 상세 설명

**folder** — 폴더 메뉴
- 사용자가 `/www/about`에 접근하면 `03.menu-management` 미들웨어가 첫 자식 메뉴로 자동 리다이렉트합니다.
- `value` 필드는 비어있습니다.

**board** — 게시판 메뉴
- `value`에 게시판 ID(예: `notice_board`)가 들어있습니다.
- 백엔드의 `cms_board_master` 테이블에서 설정을 읽어옵니다.
- 세 가지 화면 모드: `list`(목록), `view`(상세), `write`(작성)

**content** — 콘텐츠 메뉴
- `value`에 콘텐츠 ID가 들어있습니다.
- 관리자가 에디터로 작성한 HTML을 그대로 보여줍니다.

**script** — 직접 만든 페이지
- `value`는 라우팅 경로 힌트 역할입니다.
- `pages/{site}/` 폴더에 Vue 파일을 직접 만들어야 합니다.
- 예: 신청 폼 페이지는 `pages/www/half/apply.vue` 로 만듭니다.
- `[...slug].vue`의 catch-all 라우터를 우회하고 Vue Router가 직접 처리합니다.

**link** — 링크 메뉴
- `value`에 URL이 들어있습니다.
- `03.menu-management` 미들웨어가 해당 URL로 리다이렉트합니다.

## 4. 게시판 시스템 쉽게 이해하기

### boardType이 뭔가요?

관리자가 게시판을 만들 때 `boardType`을 설정합니다. 형식은 `"타입.테마"` 입니다.

```
"LIST.default"   → 목록형 게시판 + default 테마
"GALLERY.default" → 갤러리형 게시판 + default 테마
"FLOW.default"   → 플로우형 게시판 + default 테마
"LIST.qna"       → 목록형 게시판 + qna(질의응답) 테마
```

`Board.vue`는 이 값을 파싱해서 렌더할 컴포넌트 경로를 계산합니다.

```ts
// components/render/board/Board.vue
const type  = rawBoardType.split(".")[0].toLowerCase();  // "list"
const theme = rawBoardType.split(".")[1]?.toLowerCase() || "default";  // "default"

// 렌더할 Loader 경로 계산
const key = `/components/theme/${type}/${theme}/${pageSegment}/Loader.vue`;
// 예: /components/theme/list/default/list/Loader.vue
```

### 테마가 뭔가요?

**같은 데이터를 다른 디자인으로 보여주는 것**입니다. 사람이 옷을 갈아입는 것과 같습니다.

예를 들어 공지사항 데이터는 동일해도:
- `LIST.default` 테마 → 번호/제목/등록자/날짜/조회수 표 형식
- `LIST.qna` 테마 → 질문/답변 스타일

각 테마 폴더 구조:

```
components/theme/
├── list/
│   ├── default/          ← LIST.default 테마
│   │   ├── metadata.json ← 테마 메타정보 (지원 옵션 목록)
│   │   ├── list/
│   │   │   ├── Loader.vue  ← 진입점 (오버라이드 처리)
│   │   │   └── Ori.vue     ← 실제 UI 구현
│   │   ├── view/
│   │   │   ├── Loader.vue
│   │   │   └── Ori.vue
│   │   └── write/
│   │       ├── Loader.vue
│   │       └── Ori.vue
│   └── qna/              ← LIST.qna 테마
│       ├── list/
│       └── write/
├── gallery/
│   └── default/
└── flow/
    └── default/
```

### 모드(Mode)란?

같은 게시판이 세 가지 화면을 가집니다.

| 모드 | 설명 | URL 예시 |
|---|---|---|
| `list` | 게시물 목록 | `/www/notice` |
| `view` | 게시물 상세 | `/www/notice?mode=view&idx=123` |
| `write` | 게시물 작성/수정 | `/www/notice?mode=write` |

`Board.vue`가 URL 쿼리를 보고 `pageSegment`를 결정합니다.

```ts
// components/render/board/Board.vue
const pageSegment = computed(() => {
  if (isListPage.value)  return "list";
  if (isViewPage.value)  return "view";
  if (isWritePage.value) return "write";
  return "list";
});
```

### Loader.vue와 Ori.vue의 역할 분리

**Loader.vue** — "입구"입니다. 메뉴 ID별 오버라이드(맞춤 커스텀)가 있는지 확인하고, 있으면 오버라이드 파일을, 없으면 Ori.vue를 보여줍니다.

```vue
<!-- components/theme/list/default/list/Loader.vue -->
<script setup>
import Ori from "./Ori.vue";
// overrides/1001.vue 같은 파일이 있으면 해당 메뉴는 커스텀 컴포넌트 사용
const overrideModules = import.meta.glob("./overrides/*.vue", { eager: true });
const { resolvedComponent } = useMenuOverride(Ori, overrideModules);
</script>
<template>
  <component :is="resolvedComponent" />
</template>
```

**Ori.vue** — "실제 UI"입니다. 검색, 목록 테이블, 페이지네이션 등을 구현합니다.

```vue
<!-- components/theme/list/default/list/Ori.vue -->
<template>
  <div>
    <themeCommonListSearchBox />
    <themeCommonListBoardTable :items="boardList" :columns="columns" />
    <themeCommonListPagination />
    <themeCommonListActionButton />
  </div>
</template>
```

### 게시판 동적 테이블

게시판은 고정 테이블이 아닙니다. 관리자가 게시판을 만들면 **백엔드가 물리 DB 테이블을 자동으로 생성**합니다.

- `cms_board_master` 테이블에 게시판 설정 저장 (boardId = "notice_board")
- `BoardSchemaDaoImpl.createBoardTable()`이 실제 `board_notice_board` 테이블을 DDL로 생성

```java
// repository/cms/core/board/impl/BoardSchemaDaoImpl.java
public String physicalName(String boardId) {
    return "board_" + boardId;  // "notice_board" → "board_notice_board"
}

public boolean createBoardTable(Long masterIdx, String boardId) {
    String table = tableName(boardId);   // "board_notice_board"
    if (exists(table)) return false;
    // DDL 실행으로 테이블 생성
    jdbc.getJdbcTemplate().execute(ddl);
}
```

왜 이렇게 만들었냐면: 게시판마다 필드(컬럼)가 다를 수 있기 때문입니다. 일반 공지사항은 제목/내용만 있지만, 어떤 게시판은 분류/지역/날짜 같은 커스텀 필드가 필요합니다. 동적 테이블을 사용하면 각 게시판이 독립적인 구조를 가질 수 있습니다.

## 5. 나는 퍼블리셔인데, 뭘 하면 되나요?

### www 사이트 CSS 수정

www 사이트(사용자용)는 **전통 CSS**를 사용합니다. Tailwind를 절대 사용하지 마세요. 이유는 www 사이트가 서버에서 정적 CSS 파일을 직접 로드하기 때문입니다. Tailwind를 쓰면 클래스 스캔이 안 됩니다.

클래스 이름 예시 (기존 패턴을 반드시 따르세요):

```css
/* assets/css/common/common.css 또는 사이트별 CSS 파일 */
.btn_base         /* 기본 버튼 */
.btn_base.xlg     /* 큰 버튼 */
.write_box        /* 작성 폼 영역 */
.w_tit            /* 섹션 제목 */
.w_cnt            /* 섹션 내용 */
.board_error      /* 에러 메시지 영역 */
```

### GNB / LNB 디자인 변경

사이트별 헤더, GNB, LNB, 사이드바 컴포넌트 위치:

```
components/www/
├── main/           ← 메인 페이지(홈)용 컴포넌트
│   ├── Header.vue       → 메인 헤더
│   ├── GnbMenu.vue      → 글로벌 내비게이션 바
│   ├── Footer.vue       → 푸터
│   └── Sidebar.vue      → 사이드바
└── sub/            ← 서브 페이지용 컴포넌트
    ├── Header.vue        → 서브 헤더
    ├── Sidebar.vue       → LNB(좌측 서브 메뉴)
    ├── Breadcrumb.vue    → 브레드크럼
    └── Footer.vue        → 푸터
```

레이아웃 파일에서 이 컴포넌트들을 조합합니다.

```
layouts/www-main.vue  → Header + GnbMenu + <slot> + Footer 조합
layouts/www-sub.vue   → Header + Sidebar(LNB) + Breadcrumb + <slot> + Footer 조합
```

### 새 테마 만들기

기존 테마를 복사해서 이름만 바꾸면 됩니다.

```bash
# 예: list 타입에 "simple" 테마 추가
cp -r components/theme/list/default components/theme/list/simple
```

복사 후 할 일:
1. `components/theme/list/simple/metadata.json` — 테마 이름과 지원 옵션 수정
2. `components/theme/list/simple/list/Ori.vue` — 목록 UI 수정
3. `components/theme/list/simple/view/Ori.vue` — 상세 UI 수정
4. `components/theme/list/simple/write/Ori.vue` — 작성 UI 수정

관리자 화면에서 게시판의 `boardType`을 `"LIST.simple"`로 설정하면 새 테마가 적용됩니다.

**주의**: Loader.vue는 특별한 이유가 없으면 수정하지 않아도 됩니다. 오버라이드 파일 처리 로직이 있어서 그대로 두면 됩니다.

### CSS 실시간 편집기 사용법

관리자 사이트(`/business`)에 CSS 실시간 편집기가 있습니다.

- 경로: `/business/homepage/style` (관리자 로그인 필요)
- 기능: CSS 파일 열기, 수정, 저장
- 백엔드 API: `GET /back-api/admin/css/read`, `PUT /back-api/admin/css/save`
- 저장 시 `css-version.json`의 버전 번호가 자동 갱신됩니다.

**캐시 버스팅**: `useVersionedCss.ts` 유틸이 CSS URL에 `?v=버전번호`를 자동으로 붙입니다. CSS를 저장하면 버전이 올라가서 브라우저 캐시를 무효화합니다.

```ts
// composables/useVersionedCss.ts
export function useVersionedCss(paths: string[]) {
  return paths.map(href => ({
    href: `${base}${href}?v=${cssVersion.value}`,  // ?v=20240101120000
    rel: "stylesheet",
  }));
}
```

### API 호출: `safeFetch` 사용법

모든 API 호출은 `utils/safeFetch.ts`의 `safeFetch` 함수를 사용합니다. 직접 `fetch()`를 쓰지 마세요.

`safeFetch`가 자동으로 처리하는 것들:
- SSR/CSR에 맞는 API 베이스 URL 선택
- `X-Site-Hostname`, `X-Menu-Id` 헤더 자동 추가 (현재 사이트/메뉴 컨텍스트 전달)
- `XSRF-TOKEN` 쿠키 → `X-XSRF-TOKEN` 헤더 자동 추가
- 401/403 응답 → 로그인 페이지 리다이렉트 자동 처리
- 타임아웃 처리 (기본 2초)
- 중복 요청 방지 (동일 URL 동시 요청은 캐싱)

```ts
// 사용 예시 (GET)
const res = await safeFetch<{ code: number; message: string; data: MyType[] }>(
  "/my-api/list",
  { timeout: 5000 }
);
if (res.code === 200) {
  console.log(res.data);
}

// POST 예시
const res = await safeFetch("/my-api/create", {
  method: "POST",
  body: { title: "제목", content: "내용" },
  credentials: "include",
});
```

응답 형식은 항상 `{ code, message, data }` 입니다. `code === 200`이면 성공입니다.

### 상태 관리: Store 역할 분리

Pinia 스토어가 4개 있습니다. 각각 독립된 역할을 합니다.

| 스토어 | 파일 | 역할 |
|---|---|---|
| `siteStore` | `stores/siteStore.ts` | 현재 사이트 정보, 사이트 목록 |
| `menuStore` | `stores/menuStore.ts` | 메뉴 트리, 현재 메뉴 ID, 브레드크럼 |
| `renderStore` | `stores/renderStore.ts` | 현재 페이지 렌더 데이터, 게시판 옵션, 권한 |
| `userStore` | `stores/userStore.ts` | 로그인 사용자 정보, 관리자 여부 |

```ts
// 컴포넌트에서 스토어 사용 예시
const siteStore = useSiteStore();
console.log(siteStore.site);              // "www"

const menuStore = useMenuStore();
console.log(menuStore.currentMenuId);     // 현재 메뉴 ID

console.log(renderStore.option?.boardType); // "LIST.default"
console.log(renderStore.permission?.write); // true/false

const userStore = useUserStore();
console.log(userStore.isGuest);           // 비로그인이면 true
console.log(userStore.isAdmin);           // level===1 이면 true
```

## 7. 나는 백엔드 개발자인데, 뭘 하면 되나요?

### Controller → Service → Repository 흐름

표준 레이어드 아키텍처를 따릅니다. eGov 프레임워크 기반이라 `EgovAbstractServiceImpl`을 상속하는 Service가 많습니다.

```
controller/cms/core/board/DynamicBoardController.java
    ↓ 위임
service/cms/core/board/impl/DynamicBoardServiceImpl.java
    ↓ 위임
repository/cms/core/board/DynamicBoardDao.java
```

컨트롤러는 얇게 유지합니다. 파라미터 바인딩, 검증, 서비스 위임만 합니다.

```java
// controller/cms/core/board/DynamicBoardController.java
@PreAuthorize("@permService.hasAccess('ACCESS')")
@GetMapping
public ResponseEntity<ApiResponse<Page<Map<String, Object>>>> getList(
        @Valid @ModelAttribute SearchOption option,
        @Valid @ModelAttribute PaginationOption pagination,
        BindingResult bindingResult
) throws Exception {
    // 검증 실패 시 바로 400 반환
    if (bindingResult.hasErrors()) {
        return ResponseEntity.badRequest().body(ApiResponse.error(400, msg));
    }
    // 서비스에 위임
    Page<Map<String, Object>> result = dynamicBoardService.getList(option, pagination);
    return ResponseEntity.ok(ApiResponse.success(result));
}
```

### 새 API 추가 시 체크리스트

1. **패키지 위치 확인**: `controller/cms/core/{기능}/` 또는 `controller/auth/` 또는 `controller/common/`
2. **RequestMapping**: `/back-api/{기능명}` 형식 유지
3. **권한 애노테이션**: `@PreAuthorize("@permService.hasAccess('ACCESS')")` 적용
4. **응답 형식**: 반드시 `ApiResponse<T>` 래핑

```java
// 응답 형식 (dto/common/ApiResponse.java)
ApiResponse.success(data)          // { code: 200, message: "성공", data: ... }
ApiResponse.created(data)          // { code: 201, message: "리소스 생성 성공", data: ... }
ApiResponse.error(400, "메시지")   // { code: 400, message: "메시지", data: null }
```

5. **DTO 생성**: `dto/cms/core/{기능}/request/`, `dto/cms/core/{기능}/response/` 에 위치
6. **X-Menu-Id 헤더 활용**: 프론트엔드는 모든 요청에 현재 메뉴 ID를 헤더로 전송합니다. `RenderService`는 이 헤더로 어떤 게시판인지 식별합니다.

### 권한 체계

`@permService.hasAccess('LEVEL')` 에서 LEVEL은 4가지입니다.

| 레벨 | 설명 |
|---|---|
| `ACCESS` | 페이지 접근 권한 (목록 보기) |
| `VIEW` | 상세 보기 권한 |
| `WRITE` | 작성 권한 |
| `MODIFY` | 수정/삭제 권한 |

권한 설정은 관리자 화면 → 메뉴 권한 설정에서 합니다. 백엔드의 `PermissionController`가 처리합니다.

### 에러 처리

비즈니스 예외는 eGov의 `EgovBizException`을 사용합니다. 공통 예외 핸들러(`config/exception/`)가 잡아서 `ApiResponse.error()` 형식으로 변환합니다.

```java
// Service에서 비즈니스 예외 던지기
throw new EgovBizException("error.board.not_found: idx=" + idx);
```

## 8. 자주 하는 실수 & 해결법

### "로컬에서 되는데 서버에서 안 돼요"

**원인 1: CORS 문제**
- 개발 환경은 `nuxt.config.ts`의 `proxy` 설정으로 CORS를 우회합니다.
- 서버 환경은 Spring Boot의 CORS 설정(`config/common/web/`)이 적용됩니다.
- 백엔드에 현재 도메인이 허용되어 있는지 확인하세요.

**원인 2: 쿠키/JWT 설정**
- 서버에서는 HTTPS + `Secure` 쿠키가 필수입니다.
- 로컬은 HTTP라서 `Secure` 없이도 되지만, 서버는 다릅니다.
- `application.yml`의 쿠키 설정을 환경별로 분리해야 합니다.

### "메뉴가 안 떠요"

단계별로 확인하세요.

1. `siteStore.siteList`에 해당 사이트가 있는지 → `/api/json/site` API 응답 확인
2. `menuStore.menuTree`가 로딩됐는지 → `/api/json/menu?site=www` API 응답 확인
3. 메뉴의 `isShow: false`가 아닌지 → DB의 `is_show` 컬럼 확인
4. `03.menu-management` 미들웨어에서 에러가 나는지 → 브라우저 콘솔 확인

### "테마가 적용 안 돼요"

1. `boardType` 형식 확인: `"LIST.default"` (대문자 타입, 소문자 테마, 점으로 구분)
2. 파일 경로 확인: `components/theme/list/default/list/Loader.vue` 실제로 있는지
3. `Board.vue`의 콘솔 경고 확인: `"[BoardTheme] Loader not found for key: ..."`
4. `metadata.json`이 유효한 JSON인지 확인

### "API 403이 떠요"

1. `@PreAuthorize` 권한 레벨 확인: 로그인 사용자에게 해당 권한이 있는지
2. IP 화이트리스트 확인: `siteStore`의 `allowIp`, `denyIp` 설정
3. `__ipBlock=1` 쿠키가 브라우저에 있으면 → 쿠키 삭제 후 재시도
4. JWT 토큰 만료 여부: `userStore.isGuest`가 true면 토큰이 없거나 만료된 것

### "CSS 변경이 반영 안 돼요"

1. 관리자 CSS 편집기로 저장했는지 확인 (저장 시 버전 자동 갱신)
2. `useVersionedCss()`를 통해 로드하는 CSS인지 확인
3. 직접 `public/` 폴더의 파일을 수정했다면: 서버 배포 후 적용
4. 브라우저 강제 새로고침: `Ctrl+Shift+R`
5. CSS URL에 `?v=` 쿼리스트링이 붙어있는지 개발자 도구 Network 탭에서 확인

### "SSR에서 무한 리다이렉트가 돼요"

미들웨어에서 `navigateTo()`를 여러 번 호출하면 발생합니다. 해결책은 이미 코드에 있는 패턴을 따르세요.

```ts
// SSR에서 리다이렉트는 단 1회만 허용
const once = useState<boolean>("__ssr_menu_redirected__", () => false);
if (once.value) return;
once.value = true;
return navigateTo(path, { redirectCode: 302 });
```
