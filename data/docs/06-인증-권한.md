# 인증 및 권한

## 인증 아키텍처

Q-CMS는 **Hybrid JWT + Redis Session** 모델을 사용한다. JWT는 무상태 전송 수단이고, Redis가 세션 상태를 관리한다.

- JWT: 서명 검증 + 클레임 전달 (Authorization 헤더가 아닌 **HttpOnly 쿠키** 사용)
- Redis: 세션 유효성 + 서버사이드 제어 (강제 로그아웃, 실시간 권한 반영)
- **화이트리스트 전략**: Redis에 유효한 세션만 저장. 세션 없음 = 무효 토큰

## 로그인 흐름

```
POST /back-api/auth/login { username, password }
  │
  ▼
AuthServiceImpl.login():
  1. Member DB 조회 (userId)
  2. Pbkdf2PasswordEncoder로 비밀번호 검증
  3. SessionManager.createSession()
     → UUID 기반 sessionId 발급
     → Redis에 SessionData 저장 (키: sess:{sid}, TTL: 1시간)
     → 사용자 세션 인덱스 추가 (키: user:{userId}:sessions, SET 타입)
  4. JwtTokenProvider.createToken()
     → Access Token 생성 (Claims: idx, userLevel, userName, sid)
     → Redis 정상: TTL 900초 (15분)
     → Redis 장애: TTL 3600초 (1시간, fallback)
  5. JwtTokenProvider.createRefreshToken()
     → Refresh Token 생성 (Claims: sid만)
     → TTL 86400초 (24시간)
  6. AuthCookieUtil로 쿠키 설정
     → ACCESS 쿠키 (HttpOnly, SameSite=Lax)
     → REFRESH 쿠키 (HttpOnly, SameSite=Lax)
     → SESSION-EXPIRES 쿠키 (HttpOnly=false, 프론트엔드 타이머용)
  7. lastLoginDate 업데이트
```

## 요청 인증 흐름 (JwtAuthenticationFilter)

`OncePerRequestFilter`를 확장하여 **모든 요청**을 인터셉트한다.

```
요청 수신
  │
  ├─ 1. IP 접근 제어 (SiteAccessChecker)
  │     차단 시 403 응답
  │
  ├─ 2. 쿠키에서 Access Token 추출
  │
  ├─ 3-A. Access Token 유효:
  │     ├─ JWT 서명 + 만료 검증
  │     ├─ Redis 세션 조회 (sid)
  │     │   ├─ 세션 존재 → touchSession() (슬라이딩 TTL 연장)
  │     │   ├─ 세션 없음 → GUEST 처리
  │     │   └─ Redis 장애 → Degraded 모드 (토큰만으로 인증)
  │     ├─ SecurityContext에 인증 정보 설정
  │     └─ X-Session-Expires 헤더 + 쿠키 설정
  │
  ├─ 3-B. Access Token 만료 (ExpiredJwtException):
  │     ├─ Refresh Token 추출 및 검증
  │     ├─ Refresh Token의 sid로 Redis 세션 조회
  │     ├─ 세션 유효 → 새 Access Token 발급 + 쿠키 재설정
  │     └─ 세션 무효 → GUEST 처리
  │
  ├─ 3-C. 토큰 없음:
  │     └─ GUEST 사용자 생성 (idx=-1, level=GUEST)
  │
  ├─ 4. 관리자 접근 체크
  │     사이트 닫힘 + 비관리자 → 허용 경로 외 차단
  │
  └─ 5. filterChain.doFilter() → Controller 진입
```

## Graceful Degradation (Redis 장애 대응)

3가지 운영 모드:

| 모드 | 조건 | 동작 |
|---|---|---|
| Normal | Redis 정상 | JWT 서명 + Redis 세션 검증 |
| Degraded | Redis 장애 | JWT 서명 + 만료만 검증, 세션 검증 생략 |
| Recovered | Redis 복구 | 자동으로 Normal 모드 복귀 |

Redis 장애 시:
- `RedisHealthChecker.isRedisHealthy()` → false
- Access Token TTL을 3600초로 연장 (fallback)
- 세션 검증 생략, 토큰 자체만으로 인증
- 모든 사용자가 최소 권한으로 강등

`RedisHealthChecker`:
- 헬스체크 타임아웃: 500ms
- `AtomicBoolean`으로 스레드 안전한 상태 캐싱
- `isCachedRedisHealthy()`로 빈번한 호출 최적화

## JWT 토큰 구조

### Access Token

```
알고리즘: HS256
Claims:
  idx       : 사용자 ID (Long)
  userLevel : 사용자 레벨 (숫자)
  userName  : 사용자명
  sid       : 세션 ID (Redis 키)
  exp       : 커스텀 만료 시간 (epoch seconds)

유효시간: 900초 (15분)
Redis 장애 시: 3600초 (1시간, fallback)
Clock Skew 허용: 60초
```

### Refresh Token

```
Claims:
  sub : 사용자 ID (문자열)
  sid : 세션 ID

유효시간: 86400초 (24시간)
```

**블랙리스트 없음**: Redis 세션 삭제 = 즉시 토큰 무효화 (화이트리스트 방식)

## Redis 세션 관리 (SessionManagerImpl)

### 키 구조

```
sess:{sessionId}           → SessionData (JSON)     TTL: 1시간
user:{userId}:sessions     → SET<sessionId>         사용자별 세션 목록
```

### 핵심 메서드

| 메서드 | 동작 |
|---|---|
| `createSession(member, hostname)` | UUID 발급, SessionData 저장, 사용자 인덱스 추가 |
| `getSession(sid)` | Redis 조회, 장애 시 Optional.empty() 반환 |
| `touchSession(sid)` | TTL 연장 (슬라이딩 윈도우) |
| `getSessionTtl(sid)` | 남은 TTL 초 반환 |
| `deleteSession(sid)` | 단일 세션 삭제 |
| `deleteAllSessionsForUser(userId)` | `user:{userId}:sessions`에서 모든 sid 조회 → 일괄 삭제 |
| `isRedisHealthy()` | Redis 연결 상태 확인 |

### 강제 로그아웃

```
deleteAllSessionsForUser(userId):
  1. user:{userId}:sessions (SET)에서 모든 sessionId 조회
  2. 각 sess:{sid} 키 삭제
  3. user:{userId}:sessions 키 삭제
  → 해당 사용자의 모든 토큰 즉시 무효화
```

## 쿠키 관리 (AuthCookieUtil)

| 쿠키 | HttpOnly | 용도 |
|---|---|---|
| ACCESS | true | Access Token 저장 |
| REFRESH | true | Refresh Token 저장 |
| SESSION-EXPIRES | false | 프론트엔드 세션 타이머 (epoch seconds) |
| XSRF-TOKEN | false | CSRF 토큰 (Spring Security) |

속성: `SameSite=Lax`, `Secure` (HTTPS 시), `Path=/`

`X-Session-Expires` 헤더도 함께 설정하여 프론트엔드가 세션 만료 카운트다운을 표시한다.

## Spring Security 설정

파일: `config/security/JwtSecurityConfig.java`

### 필터 체인 순서

```
요청 → XssProtectionFilter → JwtAuthenticationFilter → Controller
```

### 공개 API (인증 불필요)

```java
.requestMatchers("/back-api/auth/login").permitAll()
.requestMatchers("/back-api/auth/logout").permitAll()
.requestMatchers("/back-api/render/**").permitAll()
.requestMatchers("/back-api/json/**").permitAll()
.anyRequest().authenticated()
```

### 보안 설정

```
세션: STATELESS (JWT 사용)
CSRF: CookieCsrfTokenRepository (HttpOnly=false), 로그인 예외
CORS: 전체 Origin 허용 + credentials
헤더:
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  HSTS: max-age=31536000; includeSubDomains
  CSP: default-src 'self'; script-src 'self' 'unsafe-inline' ...
비밀번호: PBKDF2 (반복 185,000회, 키 256비트)
```

## 권한 시스템

### 권한 타입

| 타입 | 설명 |
|---|---|
| VIEW | 조회 |
| WRITE | 작성 |
| MODIFY | 수정 |
| REMOVE | 삭제 |
| MANAGE | 관리 |
| ACCESS | 접근 |
| REPLY | 답글 |
| ADMIN | 관리자 전용 |

### Subject 타입

| 타입 | 설명 |
|---|---|
| LEVEL | 사용자 레벨 기준 (ADMIN=1, USER, GUEST=11) |
| ID | 특정 사용자 ID 기준 |

### 권한 체크 흐름 (PermissionServiceImpl)

```
hasAccess(permissionType, postId):
  1. 관리자(ADMIN) → 무조건 허용
  2. 현재 사용자의 메뉴 권한 조회
  3. permissionType별 허용 여부 확인
  4. postId가 있으면 작성자 여부도 확인
  5. GUEST(LEVEL:11)는 WRITE/MODIFY/REMOVE 불가
```

### 권한 상속 (PermissionResolverServiceImpl)

메뉴 계층에서 가장 가까운 조상의 권한을 상속받는다.

```
getPermissionByMenu(user):
  1. 현재 메뉴의 pathId 조회 (예: "1.3.8")
  2. 경로 파싱: ["1", "1.3", "1.3.8"]
  3. 각 경로의 권한 조회 (Redis 캐시 우선)
  4. 거리 기반 우선순위: 가까운 조상 > 먼 조상
  5. 타입 우선순위: ID 기반 > LEVEL 기반
  6. 최종 권한 맵 반환
```

### 권한 캐싱

```
Redis 키: perm:menu:{menuId}:{pathId}
TTL: 24시간
무효화: 메뉴 트리 동기화 시 해당 메뉴 + 모든 자손의 캐시 삭제
```

## Redis 사용 정리

### 키 프리픽스 (RedisConstants)

| 프리픽스 | 용도 | TTL |
|---|---|---|
| `sess:{sid}` | 세션 데이터 | 1시간 (슬라이딩) |
| `user:{userId}:sessions` | 사용자별 세션 인덱스 | - |
| `perm:menu:{menuId}:{pathId}` | 메뉴 권한 캐시 | 24시간 |
| `view:{boardId}:{postIdx}:{sessionKey}` | 조회수 중복 방지 | 24시간 |

### RedisTemplate 빈 (RedisConfig)

| 빈 | 용도 |
|---|---|
| `sessionRedisTemplate` | SessionData 전용 (JSON 직렬화) |
| `redisTemplate` (@Primary) | MenuPermissionData 전용 (JSON 직렬화) |

키: `StringRedisSerializer`, 값: `GenericJackson2JsonRedisSerializer`

## IP 접근 제어

**2중 체크:**
1. 프론트엔드 미들웨어 01.site-init (SSR) — 사이트별 allowIp/denyIp
2. 백엔드 JwtAuthenticationFilter — SiteAccessChecker, CIDR 매칭

## XSS 방어

**입력**: `XssProtectionFilter` → `XssProtectionRequestWrapper`로 파라미터/바디 새니타이징
**출력**: `@SanitizeHtml` + `HtmlSanitizerAspect` AOP → `HtmlSanitizerUtil` (OWASP HTML Sanitizer)
