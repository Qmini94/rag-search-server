# 트러블슈팅

Q-CMS 개발 및 운영 중 자주 발생하는 문제와 해결 방법을 정리한다.

## 1. 프론트엔드 이슈

### SSR/CSR 하이드레이션 에러

#### 증상

브라우저 콘솔에 다음과 같은 에러가 출력된다.

```
[Vue warn]: Hydration completed but contains mismatches.
[Vue warn]: Hydration node mismatch
```

또는 페이지가 깜박이거나 레이아웃이 순간적으로 틀어진다.

#### 원인

SSR(서버)에서 렌더링한 HTML과 CSR(브라우저)에서 Vue가 하이드레이션할 때의 DOM 구조가 다르다.
주요 원인:
- `Math.random()`, `Date.now()` 등 비결정적 값을 SSR/CSR 양쪽에서 직접 사용
- `process.client` 분기 없이 `window`, `document` 객체에 SSR에서 접근
- Pinia `persistedstate`가 SSR과 CSR의 초기 상태를 다르게 복원

#### 해결

```typescript
// 잘못된 패턴 — SSR/CSR 값이 다름
const id = Math.random()

// 올바른 패턴 — 클라이언트에서만 실행
const id = ref(0)
onMounted(() => { id.value = Math.random() })

// window 접근은 onMounted 또는 process.client 가드 사용
if (process.client) {
  window.scrollTo(0, 0)
}
```

`nuxt.config.ts`에서 SSR을 비활성화하면 임시 우회할 수 있지만 SEO와 성능에 영향이 있어 권장하지 않는다.

### 미들웨어 체인 에러 (01~05 순서 관련)

#### 증상

페이지 접속 시 무한 리다이렉트가 발생하거나, 예상과 다른 페이지로 이동한다. 또는 콘솔에 `Maximum call stack` 에러가 보인다.

#### 원인

미들웨어 실행 순서는 파일명의 숫자 접두사로 결정된다.

```
01.site-init → 01b.layout-setting → 02.authentication → 03.menu-management → 04.permission-check → 06.color-mode
```

각 미들웨어가 의존하는 스토어 순서:
- `01.site-init` → `siteStore.setSite()` (가장 먼저 실행 필수)
- `02.authentication` → `userStore` (사이트 정보 필요)
- `03.menu-management` → `menuStore.fetchMenuTree()` (사이트 정보 필요)
- `04.permission-check` → `renderStore.fetchRenderData()` (메뉴 ID 필요)

루프 방지 키가 정상 동작하는지 확인한다.

| 미들웨어 | 루프 방지 방식 | 키 |
|---|---|---|
| 01.site-init | 쿠키 | `__ipBlock` |
| 02.authentication | 쿼리 파라미터 + useState | `redirected=1` |
| 03.menu-management | useState | `__ssr_menu_redirected__` |
| 04.permission-check | useState + 쿼리 파라미터 | `__ssr_403_redirect__` |

#### 해결

```typescript
// 미들웨어 파일: middleware/03.menu-management.global.ts
// SSR 렌더당 1회만 리다이렉트 허용
const redirected = useState('__ssr_menu_redirected__', () => false)
if (redirected.value) return
redirected.value = true
return navigateTo(firstChildPath, { redirectCode: 301 })
```

- 폴더 메뉴 하위에 `isShow=true`인 자식 메뉴가 없으면 무한 루프가 발생한다. 관리자에서 메뉴 노출 여부를 확인한다.
- CSR에서만 루프가 발생하면 `navigateTo({ replace: true })`가 정상적으로 사용되었는지 확인한다.

### 메뉴가 안 뜨는 경우 (renderStore, siteStore 관련)

#### 증상

페이지에 메뉴가 전혀 표시되지 않거나, 브레드크럼(빵가루)이 비어 있다.

#### 원인

`01.site-init` 미들웨어에서 `siteStore.setSite()`가 호출되지 않았거나, `03.menu-management`에서 `menuStore.fetchMenuTree()`가 실패했다.

#### 해결

확인 순서:

```
1. URL 경로에서 사이트명이 올바르게 추출되는지 확인
   → /www/notice → 사이트명: "www"
   → Vue Devtools에서 siteStore.site 값 확인

2. 브라우저 Network 탭에서 메뉴 API 요청 확인
   → GET /api/json/menu?site=www (200 OK + 메뉴 데이터)
   → 실패 시 서버의 JSON 캐시 파일 확인:
      /data/jh_half/shared/json/{siteHostname}/menu-tree.json

3. menuStore.lastLoadedSite 확인
   → 이전 사이트와 같으면 재로드를 스킵하므로,
      사이트 전환 후에도 이전 메뉴가 보일 수 있다

4. 관리자에서 메뉴 트리 저장 버튼을 클릭해 JSON 캐시 재생성
```

`renderStore.data`가 비어 있는 경우 `04.permission-check`에서 `fetchRenderData()`가 스킵되었을 수 있다. 스킵 조건을 확인한다.

```typescript
// middleware/04.permission-check.global.ts
// 아래 조건 중 하나라도 해당되면 렌더 데이터를 가져오지 않는다
const skip =
  isRootPage ||        // /www 등 사이트 루트
  !currentMenuId ||    // 메뉴 매칭 실패
  isCommonPath         // /common/* 영역
```

### 테마 로딩 실패 (Loader.vue 오버라이드 경로 오류)

#### 증상

게시판 페이지 접속 시 빈 화면이 표시되거나, 콘솔에 다음 에러가 출력된다.

```
Failed to resolve component: ...
Cannot find module '~/components/theme/list/default/list/Loader.vue'
```

#### 원인

`Board.vue`에서 테마를 동적으로 로드할 때 경로 계산 오류가 발생한다. `boardType` 형식이 잘못되었거나 파일이 실제로 없는 경우이다.

테마 로딩 경로 규칙:

```
boardType = "LIST.default"
  → type  = "list"
  → theme = "default"
  → 로드 경로: components/theme/list/default/{mode}/Loader.vue
               components/theme/list/default/{mode}/Ori.vue

boardType = "GALLERY.default"
  → components/theme/gallery/default/{mode}/Loader.vue
```

`overrides/` 서브디렉토리를 사용하는 경우 경로가 한 단계 더 깊어진다.

#### 해결

```bash
# 1. boardType 값 확인 (관리자 > 게시판 설정)
#    형식: {대문자타입}.{테마이름}
#    예: LIST.default, GALLERY.default, FLOW.default

# 2. 실제 파일 존재 여부 확인
ls data/sources/frontend/components/theme/list/default/list/
# Loader.vue, Ori.vue 가 있어야 한다

# 3. renderStore 응답 확인
#    GET /back-api/render 응답에서 option.boardType 값 확인
curl -s "http://localhost:8080/back-api/render" \
  -H "X-Menu-Id: {menuId}" | jq '.option.boardType'
```

`metadata.json`이 없거나 Zod 스키마 검증에 실패해도 테마 로딩이 중단될 수 있다.

### 레이아웃 선택 오류

#### 증상

관리자 페이지가 사용자 레이아웃으로 렌더링되거나, www 사이트가 default 레이아웃으로 표시된다.

#### 원인

`01b.layout-setting.global.ts` 미들웨어에서 URL 깊이와 사이트명으로 레이아웃을 결정한다.

```
선택 로직:
  URL /www       → depth=1 → "www-main"
  URL /www/notice → depth=2 → "www-sub"
  URL /business/... → 항상 "business-sub"

폴백 체인:
  {prefix}-{main|sub} → default-{main|sub} → default-sub → default
```

레이아웃 파일이 `layouts/` 디렉토리에 실제로 존재하지 않으면 폴백으로 내려간다.

#### 해결

```bash
# 1. 레이아웃 파일 목록 확인
ls data/sources/frontend/layouts/
# www-main.vue, www-sub.vue, business-sub.vue 등이 있어야 한다

# 2. to.meta.layout 값 확인 (Vue Devtools > Router)
#    미들웨어 01b에서 설정한 값이 맞는지 확인

# 3. slugify() 결과 확인
#    사이트명에 특수문자가 있으면 레이아웃 프리픽스가 달라질 수 있다
```

`import.meta.glob()`으로 물리 레이아웃 파일 Set을 구축하므로, 새 레이아웃 파일 추가 후 Nuxt 개발 서버를 재시작해야 반영된다.

## 2. 백엔드 이슈

### JWT 토큰 만료/갱신 문제

#### 증상

로그인 후 15분이 지나면 API 호출이 401을 반환한다. 또는 자동 갱신이 되지 않아 매번 재로그인이 필요하다.

#### 원인

Access Token TTL이 만료되었는데 Refresh Token으로 자동 갱신이 실패했다.

주요 토큰 TTL 설정:

| 토큰 | TTL | 설정 키 |
|---|---|---|
| Access Token | 900초 (15분) | `jwt.access-token-validity` |
| Refresh Token | 86400초 (24시간) | `jwt.refresh-token-validity` |
| Redis 세션 | 3600초 (1시간, 슬라이딩) | `jwt.session-ttl-seconds` |
| Fallback Token | 3600초 (Redis 장애 시) | `jwt.fallback-token-validity` |

관련 파일: `src/main/java/kr/co/itid/cms/config/security/JwtAuthenticationFilter.java`

#### 해결

자동 갱신 흐름 확인:

```
요청 → Access Token 만료(ExpiredJwtException)
  → Refresh Token 추출
  → Refresh Token의 sid로 Redis 세션 조회
  → 세션 유효 → 새 Access Token 발급 + ACCESS 쿠키 재설정
  → 세션 무효 → GUEST 처리 (재로그인 필요)
```

```bash
# Redis에서 세션 직접 확인
docker exec -it jh-redis redis-cli -a "Yubi!!@@##64" \
  KEYS "sess:*"

# 특정 세션 TTL 확인
docker exec -it jh-redis redis-cli -a "Yubi!!@@##64" \
  TTL "sess:{sessionId}"
```

Refresh Token이 만료되었거나 Redis 세션이 삭제된 경우 재로그인이 필요하다.

### 파일 업로드 실패

#### 증상

파일 업로드 시 `413 Request Entity Too Large` 또는 `500 Internal Server Error`가 반환된다.

#### 원인 1 — Nginx 크기 제한

```nginx
# /etc/nginx/conf.d/jh-half.conf
location /back-api/ {
    client_max_body_size 60M;   # 이 값이 없거나 작으면 413 발생
    proxy_pass http://127.0.0.1:8080/back-api/;
}
```

#### 원인 2 — Spring Boot 멀티파트 설정

```yaml
# src/main/resources/application.yml
spring:
  servlet:
    multipart:
      max-file-size: 50MB
      max-request-size: 50MB
```

#### 원인 3 — 업로드 디렉토리 권한 또는 경로 불일치

```bash
# 업로드 경로 확인 (application.yml)
# file.upload.base-path: /data/egovframe-cms/uploads/board

# 컨테이너 내부에서 디렉토리 존재 및 쓰기 권한 확인
docker exec -it jh-half-backend ls -la /data/egovframe-cms/uploads/
```

### 권한(Permission) 관련 403 에러

#### 증상

특정 API 또는 페이지 접근 시 `403 Forbidden`이 반환된다.

#### 원인 1 — IP 접근 제어

프론트엔드 미들웨어 `01.site-init`과 백엔드 `JwtAuthenticationFilter`에서 2중으로 IP를 체크한다.

```bash
# 사이트 설정의 allowIp/denyIp 확인
# "all" 또는 "0.0.0.0/0"이 denyIp에 있으면 allowIp에 없는 모든 IP가 차단된다

# CMS_ALLOWED_IPS 환경변수 확인
docker inspect jh-half-backend --format='{{json .Config.Env}}' | \
  python3 -c "import json,sys; env=json.load(sys.stdin); [print(e) for e in env if 'ALLOWED' in e]"
```

#### 원인 2 — 메뉴/게시판 권한 미설정

```
권한 체크 흐름:
  hasAccess(permissionType):
    1. 관리자(ADMIN, level=1) → 무조건 허용
    2. 현재 메뉴의 권한 조회 (Redis 캐시: perm:menu:{menuId}:{pathId})
    3. permissionType(ACCESS/VIEW/WRITE/MODIFY/REMOVE) 허용 여부 확인
    4. GUEST(level=11)는 WRITE/MODIFY/REMOVE 불가
```

관련 파일: `service/auth/impl/PermissionServiceImpl.java`, `PermissionResolverServiceImpl.java`

#### 해결

```bash
# 권한 캐시 초기화 (메뉴 저장 시 자동으로 무효화되지만 수동으로도 가능)
docker exec -it jh-redis redis-cli -a "Yubi!!@@##64" \
  KEYS "perm:menu:*" | xargs docker exec -i jh-redis redis-cli -a "Yubi!!@@##64" DEL

# 관리자 > 권한 관리에서 해당 메뉴/게시판 권한 재설정
```

### 게시판 CRUD 에러

#### 증상

게시글 저장 시 `500 Internal Server Error`가 발생하거나, 동적 게시판 테이블이 없다는 SQL 에러가 출력된다.

#### 원인 1 — 동적 테이블 미생성

Q-CMS의 게시판은 관리자가 필드를 정의하면 DDL(`CREATE TABLE board_{boardId}`)이 자동 실행된다. 테이블이 없으면 게시글 CRUD가 전부 실패한다.

```bash
# MySQL에서 테이블 존재 확인
docker exec -it jh-mysql mysql -uroot -p'Yubi!!@@##64' jh_half_q_cms \
  -e "SHOW TABLES LIKE 'board_%';"

# 특정 게시판 테이블 구조 확인
docker exec -it jh-mysql mysql -uroot -p'Yubi!!@@##64' jh_half_q_cms \
  -e "DESC board_{boardId};"
```

관련 파일: `repository/cms/core/board/impl/BoardSchemaDaoImpl.java`, `service/cms/core/board/impl/DynamicBoardServiceImpl.java`

#### 원인 2 — MySQL Lock 타임아웃

DDL 실행 중 Lock 대기가 발생한 경우:

```bash
# 현재 MySQL 프로세스 확인
docker exec -it jh-mysql mysql -uroot -p'Yubi!!@@##64' \
  -e "SHOW PROCESSLIST;"

# InnoDB Lock 상태 확인
docker exec -it jh-mysql mysql -uroot -p'Yubi!!@@##64' \
  -e "SELECT * FROM information_schema.INNODB_LOCKS;"
```

#### 해결

관리자에서 게시판 설정 저장을 다시 시도한다. `BoardMasterServiceImpl`에 보상 트랜잭션이 구현되어 있어 재시도로 해결되는 경우가 많다.

### Nginx 프록시 설정

#### 증상

배포 후 사이트 접속이 안 되거나, `/back-api/` 경로가 502 Bad Gateway를 반환한다.

#### 원인

Nginx 설정의 `proxy_pass` 경로가 컨테이너 포트와 일치하지 않거나, 필수 헤더가 누락되었다.

#### 해결

정상 Nginx 설정 예시:

```nginx
server {
    listen 80;
    server_name jhhalf.mx.co.kr;

    # 프론트엔드 (Nuxt SSR) — WebSocket 헤더 필수
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }

    # 백엔드 API — 파일 업로드 크기 설정 필수
    location /back-api/ {
        proxy_pass http://127.0.0.1:8080/back-api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 60M;
    }

    # 공유 정적 파일
    location /public/ {
        alias /data/jh_half/shared/public/;
        expires 7d;
        add_header Cache-Control "public, immutable";
    }
}
```

```bash
# Nginx 설정 검증 및 적용
sudo nginx -t
sudo systemctl reload nginx

# 프록시 대상 확인
curl -s http://127.0.0.1:3000/ | head -3      # 프론트엔드
curl -s http://127.0.0.1:8080/back-api/auth/login -X POST | head -3  # 백엔드

# Nginx 에러 로그
tail -50 /var/log/nginx/error.log
```

`X-Forwarded-For` 헤더가 전달되지 않으면 IP 기반 접근 제어(`01.site-init`, `JwtAuthenticationFilter`)가 올바른 클라이언트 IP를 인식하지 못한다.

### 모델 다운로드 멈춤 (lock file)

#### 증상

RAG 서버 컨테이너가 시작 시 `Loading embedding model...` 메시지 이후 아무 반응 없이 멈춘다. 또는 컨테이너가 재시작 루프에 빠진다.

#### 원인

HuggingFace 모델(`intfloat/multilingual-e5-small`) 다운로드 중 컨테이너가 강제 종료되면 `model-cache` 볼륨에 불완전한 파일이나 `.lock` 파일이 남는다. 다음 시작 시 lock 파일이 있으면 다운로드가 무한 대기 상태에 빠진다.

모델 로드 코드:

```python
# server/services/embedder.py
def get_model() -> SentenceTransformer:
    global _model
    if _model is None:
        _model = SentenceTransformer(MODEL_NAME)   # 이 줄에서 멈춤
    return _model
```

#### 해결

```bash
# 1. 현재 다운로드 상태 확인
docker logs $(docker ps | grep rag-server | awk '{print $1}') --tail 30

# 2. 모델 캐시 볼륨 내용 확인
docker volume inspect rag_model-cache
docker run --rm -v rag_model-cache:/cache alpine ls /cache/huggingface/

# 3. lock 파일 제거
docker run --rm -v rag_model-cache:/cache alpine \
  find /cache -name "*.lock" -delete

# 4. 캐시 완전 초기화 (모델 재다운로드)
docker compose -f "C:/Users/user/Desktop/Project/RAG/docker-compose.yml" down
docker volume rm rag_model-cache
docker compose -f "C:/Users/user/Desktop/Project/RAG/docker-compose.yml" up -d

# 5. 다운로드 진행 상황 모니터링
docker logs -f $(docker ps | grep rag-server | awk '{print $1}')
# "Model loaded." 메시지가 출력되면 정상
```

네트워크가 느린 환경에서는 모델 다운로드에 수 분이 걸릴 수 있다. `docker compose up` 실행 후 `docker logs -f`로 진행 상황을 확인한다.

## CSS 편집

### 잠금 충돌

#### 증상

CSS 편집 시 "다른 사용자가 편집 중입니다" 메시지가 표시된다.

#### 원인

이전 편집 세션의 Lock이 해제되지 않았다.

#### 해결

1. 잠금을 건 사용자가 편집기를 닫으면 자동 해제된다
2. 브라우저를 강제 종료한 경우 Lock이 남을 수 있다
3. 일정 시간이 지나면 Lock이 자동 만료된다

### CSS 버전 캐시 문제

#### 증상

CSS를 수정하고 저장했는데 사이트에 반영되지 않는다.

#### 원인

브라우저 캐시 또는 Nginx의 `expires` 설정으로 이전 CSS가 캐싱되어 있다.

#### 해결

1. 프론트엔드의 `useVersionedCss` composable이 CSS URL에 버전 쿼리 파라미터를 붙인다
2. 버전이 갱신되지 않았다면:
   - 관리자에서 CSS 다시 저장
   - 브라우저 강제 새로고침 (Ctrl+Shift+R)
3. Nginx 설정 확인:
   ```nginx
   location /public/ {
       expires 7d;
       add_header Cache-Control "public, immutable";
   }
   ```
   CSS 변경 시 파일명이나 쿼리스트링이 바뀌어야 캐시가 무효화된다
